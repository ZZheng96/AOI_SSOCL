# AOI_sys 重构设计：以检测引擎为算法核心

> 日期：2026-08-22 · 状态：待用户确认
> 决策记录：① 算法工程 src 拷贝进 AOI_sys 成为内部模块；② demo1/demo4 旧引擎路径彻底移除；③ UI 新增学习曲线页、槽位贡献可视化页、场景分层配置页；④ 默认工作点 fast（sem/disc/shead，2500² <200ms），精度模式可切换；⑤ 反馈即学（提交反馈立即在线更新），保留"批量巩固"按钮（累积反馈重拟合/重校准）。

## 1. 重构目标：突出赛题三大工程能力

赛题《可自学习的 AOI 实时在线 AI 质检》核心定位（报告1 §1.3）：**实时性、少样本冷启动、持续学习**三大工程能力。重构后系统的呈现与功能围绕这三点组织：

| 赛题重点 | 引擎能力支撑 | 系统呈现 |
|---|---|---|
| ① 实时视频/图片异常检测（2500²@2060 <200ms，CPU <2s） | 双工作点：fast（sem/disc/shead 全 GPU 槽，2500² ~69-100ms）/ 精度（全槽位 ~400ms）；CPU 降配（m4_cpu）| 监控页延迟对照预算标红；评估中心延迟基准；场景分层页可切换工作点 |
| ② 少样本/无样本启动（100+30 协议） | 场景分层 L0-L3（仅正常图→图像级标注→定位标注→品类→模板）；伪异常合成（disc/shead "避开异常"训练目标）| 场景分层配置页；准备模型流程按层级激活槽位 |
| ③ 用户反馈驱动优化（反馈-追溯-调整） | SSOCL：三类反馈即学、双库制、缺陷拦截通道（1-2 张即拦截）、在线权重学习、虚高重校准、回归门控回滚 | **学习曲线页（胜负手）**：AUROC/learned_acc/错→对转化率随反馈数上升；反馈页保留 |

附带：可解释性（槽位贡献可视化页：13 槽位权重、三层评价贡献档案、检测框主导槽位标注）。

## 3. 关键技术点

### 3.1 引擎适配层（仿 demo4_adapter 范式）

`DetectionEngine` 提供与原 ModelRegistry 等价的接口：`fit(category)` / `predict(image) / predict_frame(ndarray)` / `feedback(...)` / `save_snapshot(category) -> version` / `load_snapshot(category, version)` / `build_variant(version)`（A/B）/ `evaluate(category, split)` / `contribution(category)` / `learning_curve(category)`。

结果契约字段映射（后端 Detection 表适配）：
- `fused` → score；`decision`(normal/gray/anomaly) → is_anomaly + gray 态
- `boxes` → defect_boxes；`mask` → 渲染热力图 overlay（复用现有 render_heatmap_overlay）
- `slot_scores` + `router_w` → 新 JSON 字段（替代 level1/2/3_score）
- `types` → 缺陷类型归因展示（加分项：异常类型识别）

### 3.2 持久化补齐（最大改造点）

引擎 fit 后状态驻留内存，需新增 `algo/persist.py`：
- torch.save：disc/shead 头权重、孵育头
- npz/pickle：sem coreset bank、NormalBank core/ext、DefectBank、CDFCalibrator.edges、trad/layout 库
- JSON：Decider 阈值、pipe.weights、配置快照、血缘（parent_version）
- 快照目录 `storage/snapshots/{category}/v{n}/`，是模型管理/A/B 对比/回滚的基础
- 每次在线更新自动留快照（红线"更新留痕可回滚"的工程化）

### 3.3 反馈闭环语义变化

原系统："攒够 10 条反馈 → 点增量更新 → EWC 微调 AHL"。
引擎语义：**反馈即学习**（`pipe.feedback()` 内自动完成回流/拦截/权重学习/重校准，全部走回归门控+回滚）。
- `POST /api/feedback` 提交后立即触发在线更新（秒级生效，"这批错检下批检对"）
- 原"增量更新"按钮改为"批量离线巩固"（可选：用累积反馈重拟合/重校准）或移除
- 学习曲线页数据源：每次反馈更新后记录当前锚定集/验证集 AUROC → 时序落库（新表 `learning_points` 或挂 EvalRun）

### 3.4 场景分层（L0-L3）落到配置

准备模型时按可用信息选择层级 → 映射 引擎槽位激活：
- L0（仅正常图）：sem + inp + trad + blob + layout（无 disc/shead，阈值用正常分位数）
- L1a（图像级标注 ≤100+30，赛题标准）：全槽位，disc/shead 伪异常训练，sanity 加权
- L1b（+定位标注）：PRO 评测、框级反馈（反馈框 → DefectBank.add_box）
- L2（+品类）：品类级独立快照与库（系统天然按品类隔离）
- L3（+模板）：激活 tpl 槽位

### 3.5 速度红线

- 默认工作点 **fast**（m0_fast：sem/disc/shead，2500² <200ms 达标，标准数据集精度反而更高 U59）
- 精度模式（全槽位 m0）~400ms@2500²，仍在 1s 红线内，供演示/精检切换
- CPU 降配 m4_cpu（blob/trad/layout，无 DINO）<2s 挑战目标
- tiles36/shead crop 模式超红线，不作为系统默认配置暴露

## 6.1 M1 实施踩坑记录（后续改进参考）

M1 冒烟迭代 8 轮才通过，以下问题按重要度排列，均属"持久化完整性"范畴：

1. **head 训练/推理模式未随快照恢复（最隐蔽）**：`shead`/`disc` 槽位的 `head` 在 `fit()` 末尾 `self.head.eval()`，但
   `load_snapshot` 只 `load_state_dict`，槽位 `__init__` 创建的 head 保持 train 模式——dropout 随机化导致
   同图 save/load 分数差 0.38（shead 校准分 0.9922→-1.0）。修复：`_restore_slot_state` 注入权重后
   统一 `head.eval()`。教训：**任何含 dropout/BN 的模块，持久化必须显式保存/恢复 training 标志**。
2. **恢复时覆盖方法名**：`SlotWeightLearner.weights` 是**方法**（非属性），初版恢复逻辑
   `setattr(wl, "weights", dict)` 把方法覆盖成 dict，后续 `self.weight_learner.weights()` 调用崩
   `TypeError: 'str' object is not callable`。修复：恢复前 `callable(cur)` 检查跳过；保存侧也只落真实
   数据字段（slots/min_neg/n/pos/neg/n_updates/initial_weights/prior_fade/height_log/_height_flagged）。
3. **派生状态漏恢复**：`Pipeline._score_slots` 由 `cfg.fusion` 派生、不在 `__init__` 初始化
   （只在 `fit()` 入口赋值），加载快照后 predict 直接 `AttributeError`。修复：`load_snapshot`
   里按 `cfg.fusion.skip_zero_weight/only_slots` 重新派生。教训：**fit-only 初始化的属性都属于
   持久化面**，需在 persist 里统一兜底。
4. **RegressGate 基准丢失**：`base_mean/base_std/anchor_paths` 未持久化时，在线反馈链路的
   `gate.check` 因 `None` 运算崩溃。修复：新增 `ssocl/regress_gate.json` 持久化 gate 快照；
   兜底用 `_train_normal_paths` 重 setup。
5. **跨设备张量**：router 在 `_record` 里与 CPU 构造的 svec 做矩阵乘，`map_location` 加载后
   router 在 CUDA 而 svec 在 CPU → `RuntimeError: cpu and cuda:0`。修复：按
   `next(router.parameters()).device` 构造输入张量。
6. **测试断言口径**：反馈提交后的 v2 快照**含** SSCL 正常回流/CDF 重估（预期行为），与 prepare
   时分数差异**不是持久化 bug**。一致性断言必须对 prepare 完成的**纯净 v1** 做（反馈前快照）。
7. **Python 局部导入遮蔽**：函数内 `import numpy as np` 使后续对模块级 `np` 的引用被判为
   未绑定局部变量（`UnboundLocalError`）。教训：函数内 import 同名模块要换名或上移。

### 踩坑记录

1. **prepare 样本隔离红线**：init_defect（train_anomaly+test 缺陷）与 val（test 抽样）可能取到同一张 test 缺陷图，
   触发 `algo.common.isolation.guard_bundle` "fit 集与 val 集有交集" 断言。修复：`_prepare_engine` 组装 bundle 时
   把 val 路径从 init_defect 中剔除。**教训：fit/val/test 任何两集共享路径都会被强校验拦截，组装 bundle 必须显式去重。**
2. **TestClient 依赖**：本机 starlette 要求 httpx（提示装 httpx2，实际 pip install httpx 即可跑，仅有 deprecation warning）。
3. **冒烟库唯一约束**：`images.path` unique，同一张图不能以两个 split 入库（smoke 脚本需把 test 缺陷与 train_anomaly 缺陷分开取图）。
4. **feedback box 格式**：引擎侧是**归一化 [x0,y0,x1,y1]**（或 list of boxes），而前端 Feedback.region 是像素 [x,y,w,h]，
   routes_feedback 内做换算（PIL 读尺寸）；读不出图像则不带框降级为整图反馈。
5. **速度实测**（bottle 900×900，m0_fast+fast profile，GTX1660S）：prepare 全量 fit ≈8s（10+2 样本），
   单图 detect 52~348ms（含热力图渲染），反馈即学 72ms——均远低于 1s 红线。
6. **pending_update_status 口径**：即学即消费后 DB unconsumed 恒≈0，"未巩固反馈数"改以
   `pipe.handler.feedback_log` 长度为准（pipe 未加载时 None）；engine._pipes 是私有成员，
   只读访问不触发装载，M2b 可考虑在引擎层加公开访问器。

### 端点契约（供 M3 UI）

- `POST /api/learning/curve` 请求 `{category, n_stream=20, n_eval=20, feedback_ratio=1.0, eval_every=2, max_feedback=20}` → `{task_id, description}`（description 明示"离线回放不影响线上模型"）。
- `GET /api/learning/curve/{category}/latest` → `{eval_run_id, steps[], auroc[], f1[], initial_auroc, final_auroc, auroc_gain, efficiency, n_feedback}`。
- `GET /api/learning/contribution/{category}/latest` → `{univariate, redundancy, ablation}`，其中 `ablation.leave_one_out` 为每槽位剔除后 AUROC、`ablation.single` 为单槽位 AUROC、`ablation.full` 为全量融合 AUROC。
- 样本组装约定：锚定 eval 集 = test split 均衡抽样（必须同时含正常/异常，否则 400）；stream = 品类其余有标注图按 path 与 eval 集去重、异常/正常交错（避免流前段全 normal）。

### 踩坑记录

1. **stream/eval 去重必须按 path**：`images.path` 有唯一约束，同一张图不可能以两个 split 入库，但组装时仍要显式按 path 排除锚定集，防止未来约束放松后串集。
2. **A/B 样本下限从 4 降到 2**：M2 冒烟的 test 集仅 3 张（2 正常 + 1 异常），旧 `<4` 校验会让小样本品类无法对比；单一类别时 AUROC/AP 置 None、verdict 退化为 tie，不阻断。
3. **小样本 AUROC 抖动是预期**：3 张锚定图下 accuracy auroc=0.5、学习曲线在反馈=6 时锚定 AUROC 瞬降 0.0 再恢复——样本量太小（1 正 2 负）导致单个样本翻盘即 ±0.5，属统计噪声非引擎缺陷；M3 UI 展示时应提示样本量。
4. **学习回放中 CDF 重估门控频繁触发**（U62 虚高检测，drift≈0.02 ≤ tol 通过）属 引擎正常在线校准行为；回放全程走 `engine.simulate_learning` 的快照副本（`load_snapshot` 独立 pipe），线上激活 pipe 权重/校准态不被串改——已用冒烟前后检测一致性间接验证。
5. **速度实测**（bottle 900×900，fast profile，GTX1660S）：accuracy 3 图 ≈1s；ab_compare 6 次前向 + 快照加载 ≈4s；learning_curve（12 反馈 + 6 评估点 × 3 锚定图）≈30s；contribution ≈2s。学习曲线耗时 ≈ max_feedback×(predict+feedback) + (max_feedback/eval_every)×n_eval×predict，max_feedback=20 默认参数下预估 5-10s（不含每评估点锚定集前向），符合"默认走后台任务"设计。
6. **UI 遗留**：ui/api_client.py `ab_compare()` 仍发旧 `candidate_model_id` 载荷，M2b 后服务端会 422；按约束不改 UI，待 M3 统一改造。

## 6.5 M5 工业化完善方案（2026-08-22）

围绕工业实际生产需要 + 赛题三重点，选定四项完善（按价值排序）：

### A. 灰区复核队列闭环（灰区→复核→自动反馈即学）
- **动机**：工业现场灰区帧不能拦产线也不能放过，必须进人工复核队列；复核结论天然是最有价值的反馈样本（边界样本）。赛题"反馈驱动持续学习"的最强呈现。
- **后端**：`GET /api/review/queue?category=&page=` 查 `detections` 中 decision=="gray"（存于 n_tiles JSON）且尚无 feedback 的记录；`POST /api/review/{detection_id}` 复核（操作员判 normal/anomaly）→ 自动走 `submit_feedback` 即学 + 落 Feedback 表（feedback_type=review，consumed=True）。`GET /api/review/stats` 复核队列规模/今日复核数。
- **UI**：监控页 gray 徽标旁提示"已入复核队列"；反馈页加"待复核"Tab（列表+图片+一键正常/缺陷按钮）。
- **不加新表**：复用 detections + feedback 外键（feedback.detection_id 非空即已复核）。

### B. 版本激活质量门控
- **动机**：在线学习后固化的版本直接激活有"越学越差"风险；工业上线前必须回归验证。引擎已有在线侧 RegressGate，本项补**激活侧**门控。
- **后端**：`POST /api/models/{id}/activate?gate=true`：激活前用品类锚定集（train 正常抽样 20 + 已知缺陷反馈/test 缺陷抽样 20）对候选版本 `build_variant` 与当前版本平行打分，候选 AUROC < 当前 - margin(0.02) 时返回 409 + 对比数据（可 `force=true` 强制）。响应带 gate 报告（双方 AUROC/F1/分歧样本数）。
- **UI**：模型页激活按钮弹门控结果对话框（通过→确认激活；拒绝→显示对比+强制激活选项）。

### C. 检测结果 webhook 推送（MES/PLC 对接）
- **动机**：产线分拣信号/工单系统对接刚需。
- **后端**：`configs/default.yaml` 加 `notify.webhook_url`（空=禁用）+ `notify.events`（默认 ["anomaly"]，可选 gray/feedback/consolidate）。`DetectionService._persist` 后异步（线程池，不阻塞检测路径）POST JSON {event, category, detection_id, score, decision, image_path, defect_boxes, latency_ms, ts}；超时 3s、失败静默记 OperationLog。
- **UI**：不动（配置项）；用户手册补一节。

### D. 在线学习曲线（真实反馈流）
- **动机**：离线回放（simulate_learning）是"如果重来"的模拟；生产上更想看**本机真实反馈以来判对率变化**。差异化叙事："每一次复核/反馈都让下一帧更准"。
- **后端**：`GET /api/learning/online_curve/{category}`：从 DB 按时间取该品类 feedback 及其 detection（join），横轴=反馈序号 k，纵轴=滚动窗口（默认 10）判对率 + 累计反馈数分 verdict  stacked。纯 DB 计算，<100ms，无需跑模型。附当前 weight_learner 权重快照。
- **UI**：学习曲线页加"在线曲线"Tab（与离线回放并列）。

### 不做清单（明确排除，防范围蔓延）
- 多用户/权限体系（赛题 demo 单机，OperationLog 已够审计）。
- 相机 SDK（GigE/海康）直连：folder/video/camera 三模式已覆盖演示，SDK 属部署工程。
- PostgreSQL 迁移、分布式：单机 SQLite 满足节拍。
- stats_page 未巩固反馈 KPI 合并进 A 的 review/stats 顺带做。

### 接线点

- **共用即学路径**：`self_learning/service.py::submit_feedback_record(detection_id, feedback_type, operator_label, ...)` = 落 Feedback + 今日统计 + `engine.submit_feedback` + consumed=True + webhook("feedback")；`routes_feedback` 与 `routes_review` 两侧复用（routes_feedback 内原 `_map_verdict_label/_region_to_norm_box` 私有副本删除，逻辑移入 service）。
- **webhook**：`backend/core/notify.py::notify_event(event, payload)`，ThreadPoolExecutor(1) 异步 POST（requests，timeout=notify.timeout_s）；禁用=`notify.webhook_url` 为空。接线：`DetectionService._persist` 后（is_anomaly→"anomaly"，decision=="gray"→"gray"）、`submit_feedback_record` 即学成功后→"feedback"、`sl_service.consolidate` 成功后→"consolidate"。失败静默记 `OperationLog("webhook_error")`。
- **激活门控**：`evaluation/service.py::evaluate_activation_gate(category, candidate_version, margin=0.02)`；`sl_service.resolve_model_version(model_id)` 抽出供路由在门控前解析 (category, version)。
- **判对映射**（在线曲线）：`false_positive/false_negative/new_defect→错`；`confirmed→对`；`review→人工 label 与系统二分类（is_anomaly）一致为对`；review 反馈给引擎的 verdict 取 "none"（gray 未承诺二分类，以人工 label 学习）。

### 踩坑记录

1. **门控锚定集必须正负各 ≥4 才实际打分**（对方案 6.5-B 的修正）：AUROC 分辨率为 1/(n_pos×n_neg)，单侧 <4 时粒度（≥1/16 甚至 ≥1/4）已粗于 margin=0.02，小样本下"拒绝/放行"纯靠噪声，还会让既有激活链路（M2 冒烟 v1↔v2 切换）随机 409。实现为 total<4 或 min(pos,neg)<4 → skipped=True 直接放行；候选即当前激活版本也短路跳过（避免 40 张无谓前向）。
2. **SQLite JSON 字段查询**：`n_tiles` 无原生 JSON 查询，用 `cast(Detection.n_tiles, String).like('%"decision": "gray"%')` 粗筛 + Python 解析精确过滤（SQLAlchemy JSON 默认序列化带空格分隔符；注意 `cast(str)` 会报 TypeError，必须用 `sqlalchemy.String`）；已复核判定用 `feedback.detection_id` 存在性，不加新表。
3. **queue/stats 的 N+1**：每条 gray 记录一次 `_has_feedback` 查询——灰区帧量级小（产线占比低），分页前内存过滤可接受；如未来积压再改 NOT EXISTS 子查询。
4. **webhook 异步池 daemon 语义**：ThreadPoolExecutor(1) 串行推送，检测路径零阻塞；进程退出时未完成的推送直接丢弃（烟雾验证：不可达地址 ~1s 内连接拒绝落 webhook_error，检测延迟无变化）。
5. **routes_feedback 重构零行为变化**：POST /feedback 响应契约 `{id, engine_update, note}` 不变，M3 UI 的 feedback_dialog 无需改动。

### 踩坑记录

1. **alarm 窗口语义**：每"帧"= 每次 `detect_image` 调用（同一张图重复检测也会推进窗口）。这是有意语义（产线视角每次检测=一帧）；REST 单图调试时若连续测同一缺陷图会人为触发告警，演示时注意。窗口按品类隔离，跨品类不互相污染。
2. **冷却期与 active 的区别**：`fired` 只在"到达阈值且出冷却期"那一刻为 True（供 webhook/日志一次性消费）；`active` 只要窗口命中 >=k 就 True（随每帧响应/WS 下发，UI 横幅用它）。两者解耦，UI 不应依赖 fired。
3. **smoke 端到端告警的坑**：不能假设"检测缺陷图 5 张 -> is_anomaly=True"（三态判定下缺陷图可能落 gray），所以端到端分两层：单元级直接灌单例 `record()` 断言 fired/冷却/滑出；接线级直接调 `_record_alarm(CAT, True)` 灌 5 次断言 OperationLog("alarm")，REST detect 只断言 alarm 字段存在且 window_hits>=5（不绑 is_anomaly 真值）。
4. **smoke 环境无 notify 段**：`AOI_CONFIG` 指向的临时 yaml 只有 system 段，`get_alarm_cfg()` 必须带默认值（20/5/60），否则单例构造直接 KeyError。M5a 段中途还会覆写 `cfg._cfg["notify"]`（webhook 测试），alarm 单例若在此后才首次构造同样落默认值--两路径都验证过安全。
5. **precheck 的 feedback 计数口径**：`Image.split=="feedback"`（导入回流图片才有）；通过 `/api/feedback`/复核提交的反馈不生成 Image 行（只落 Detection+Feedback），故 smoke 断言 feedback=0 是预期而非漏计。

## 6.12 M7 追溯→学习→提升可视化闭环（2026-08-22）

**叙事主线**：每张被反馈的图都有"学习前判定 vs 学习后判定"两个点，连成翻案曲线——这是"反馈驱动持续学习"最直接的视觉证据。

### 核心机制：反馈时记录"反馈前判定"

- `submit_feedback_record` 在调 `engine.submit_feedback` **之前**先 `engine.predict_image_path(category, image_path)` 记 pre（score/decision/latency ~60ms，反馈路径实测 72-140ms → ~200ms 仍 <1s 红线内）；
- Feedback 表 `region` JSON 扩展（不加列）：`{"box": [x,y,w,h]|null, "pre": {"score":.., "decision":.., "slots":{..}}}`。存量反馈无 pre 字段时追溯接口降级（pre=None，曲线跳过该点）。
- 检测时 `Detection.n_tiles` JSON 已有 slots/weights/decision，天然含判定现场。

### 后端（3 个新端点，routes_learning.py 追加 + routes_feedback/review 内部增强）

1. **GET /api/learning/flip_curve/{category}**：翻案曲线。取该品类有 pre 记录的反馈，按时间升序逐条用**当前引擎**重打分该图 → post（score/decision）；point={k, image_path, pre_score, post_score, pre_decision, post_decision, flipped(bool, 与人工 label 对齐为翻案)}；summary={total, flipped_count, flip_rate}。N 条反馈 → N 次 predict（~60ms×N），N>50 时走后台任务。
2. **GET /api/detections/{id}/trace**：单帧完整追溯链。响应：detection 全字段 + 当时模型版本（join Model）+ feedbacks[]（每条含 feedback_type/label/region.pre/created_at/engine 摘要）+ 该帧后续同类判定变化（若反馈含 pre 且当前引擎对该图重打分→附 post）。
3. **GET /api/detections/misjudged?category=&page=`：错检集（有反馈且 feedback_type ∈ fp/fn/new_defect），行含 detection 摘要 + 反馈结论 + pre/post 分数（若有）。支持 `format=csv` 导出。

### UI（反馈页改造 + 追溯视图）

- **反馈页加第三 Tab「追溯与提升」**：
  - 上半：翻案曲线图（x=反馈序号 k，y=score 双折线 pre/post + 翻案点高亮圆点）+ KPI（错检数/已翻案数/翻案率）；
  - 下半：错检列表（misjudged 表格：时间/图/当时判定/反馈结论/pre→post 分数/翻案✓✗），点击行弹追溯详情对话框（大图 + 槽位分 + 反馈时间线）。
- 反馈提交/复核提交的即学摘要 toast 中追加 pre→post 对比（"该图分数 0.72→0.15"）——即时反馈感。

### 不做清单

- 不做"批量重放历史检测"（回溯所有 Detection 用当前模型重打分）：数据量不可控，翻案曲线只覆盖"被反馈的图"已足够叙事。
- 不引入新表：pre 判定塞 Feedback.region JSON，追溯靠 join。

### 关键实现与踩坑

- **region 双形态兼容**：存量行为 list（像素 box）或 None，新行为 dict。统一入口 `self_learning.service.region_box_pre(region) -> (box, pre)`：list→(list, None)，dict→(region["box"], region["pre"])。`_region_to_norm_box`、flip_curve、trace、misjudged 全部走该入口。
- **flipped 判定**：`_judge_match(decision, label)`——label=1 要求 decision=="anomaly"，label=0 要求 decision=="normal"；**gray 对两种 label 都算不一致**（系统未承诺二分类）。flipped = post 一致 ∧ pre 不一致。
- **路由顺序**：`/api/detections/misjudged` 必须注册在 `/api/detections/{detection_id}` **之前**，否则 "misjudged" 被路径参数捕获报 422。`/detections/{id}/trace` 为两段路径，天然无冲突。
- **predict 有轻量副作用（重要发现）**：`Pipeline._finalize` 每次推理都会调 `handler.normal_bank._observe_decision()` 更新在线缺陷率滑动窗（回流熔断用，窗长 200）。因此 flip_curve/trace 的重打分会把被反馈图计入在线缺陷率——反馈图多为异常图，短期内会轻微抬高 defect_ratio。评估认为可接受（窗长 200，正常检测流迅速稀释），但**不允许**在批量重放场景无节制调用 predict。
- **pre 打分时机**：必须先 predict 再 `engine.submit_feedback`（顺序反了 pre 就成了"学习后"）。反馈路径总耗时 = predict(~60-300ms) + 即学(~130ms)，实测仍 <1s 红线。
- **Detection.model_id 恒为 None**：pipeline._persist 不写 model_id，trace 的 model 字段目前总是 None（契约保留，待检测落库补写 model_id 后自动生效）。【已于 M7b 主线修补：_persist 按当前激活版本 join Model 表写入，见 6.14】
- **冒烟既有段的一处必要改动**：M6a 段原断言 `fb6.region == [10,10,50,50]`，region 结构变更后改为断言 `fb6.region["box"] == [10,10,50,50]`（功能变更的必然连带，非额外改动）。

## 6.15 M8 数据资产工业化治理方案（2026-08-22）

调研发现的核心问题：**无批次/数据集实体**，"一堆不知来源的图堆在一起"；四种拷贝策略并存；级联删除缺失；标注流转缺失；日志非结构化。对照工业实操标准（批次追溯/来源可审计/标注流转/级联清理）定以下方案。

### A. 数据集/批次实体（核心）
- 新表 `Dataset`（数据集批次）：`id, name, category, source_type(folder/mvtec/upload/pseudo/augment/video), source_path, params(JSON), n_images, note, created_at`；`Image.dataset_id` 外键（轻量加列，沿用 `_migrate_sqlite` 先例）。
- 所有导入入口（import_folder/import_mvtec/upload/pseudo 生成/增强/视频抽帧登记）强制挂批次；老数据 dataset_id=None 归入系统自动建的"历史未分组"批次。
- 端点：`GET /api/datasets`（列表含图片数/来源/时间）、`GET /api/datasets/{id}`（含图片分页）、`DELETE /api/datasets/{id}`（级联：删图片行+磁盘文件+关联检测/反馈可选保留标记，默认保留检测但解除 image_id 关联）、`POST /api/images/{id}/annotate`（改 label/split/defect_type，记 OperationLog）。
- 磁盘目录整改：`storage/images/{category}/{dataset_id}/` 分层存放新导入图（老文件不动，向后兼容）；拷贝命名加 `ds{dataset_id}_` 前缀消除冲突。

### B. 标注流转
- `POST /api/images/{id}/annotate` {label?, split?, defect_type?}：改标记日志；UI 数据页图片右键/工具栏加"标注"对话框；`val`/`feedback` split 由此入口可产生。

### C. 级联删除与孤儿治理
- `DELETE /api/images/{id}` 加 `?delete_file=true` 选项删磁盘文件；
- `DELETE /api/datasets/{id}` 级联清理该批次全部；
- `POST /api/maintenance/orphan_scan`：扫描 storage 下无 DB 引用的文件，返回清单（不自动删），`POST /api/maintenance/orphan_clean` 清理（写日志）。后台任务。

### D. 统计与日志结构化
- OperationLog 增强：`detail` 保持文本，但日志写入点统一附带结构化 JSON（`log_action(action, detail, user, extra={"image_id":..,"dataset_id":..,"category":..})`，extra 塞 detail 前缀 JSON 或新列——选新列 `extra JSON`，轻量迁移）。
- `GET /api/logs` 加 `?action=&category=` 过滤。
- stats overview/timeseries 加 `?category=` 按品类过滤（Detection.category 已有索引）。

### E. UI 数据页重构
- 图像 Tab 改左侧树四维：品类→数据集批次→split→label；表格加"批次/来源/导入时间"列；右键菜单加"标注/删除(可选删文件)"；批次节点右键"删除批次/导出清单"。
- 导入对话框加"批次名/备注"输入。

### F. 视频/反馈数据断链修补
- 视频抽帧登记 VideoFrame 表（唤醒死表）+ 帧图挂批次（source_type=video）；
- 反馈/复核的图若不在 Image 表，自动登记一行（split=feedback, dataset=系统"反馈回流"批次）。

### 不做清单
- 不做多用户权限（OperationLog.user 保留 operator 文本）。
- 不做对象存储/去重哈希升级（sha1 已有，够单机用）。
- 老数据不迁移物理目录（只登记批次关联）。

4. **timeseries 按品类的口径切换**：StatsDaily 是全局表且不改结构（不加列原则），按品类时实时从 Detection 聚合；反馈类字段（n_feedback/n_false_*）该口径下置 0（Feedback 无日期按品类直接聚合口径，留待需要时 join Detection）。

### 重要发现（后续改进参考）

1. **m0_fast.yaml 存在双 `fusion:` 键覆盖 bug**：文件第 19 行声明 `weight_mode: equal`、第 71 行又有一个 `fusion: {mode: fixed_equal}`，PyYAML 后者覆盖前者，weight_mode 声明实际被丢弃。M9 首跑等权+共识融合下 bottle AUROC 仅 0.8333；算法基线（U55/U59）均为 sanity 加权口径。【已修复】合并两个 fusion 键为单个 `fusion: {weight_mode: sanity, mode: fixed_equal}`，验收脚本直接引用修好的原文件，重跑结果一致（bottle 1.0000/cable 0.9644/tile 0.9667/screw 0.8444）。
2. **n_init_normal=20 时 AUROC 系统性低估（少样本边界量化）**：20 正常 + 5 锚定下 bottle/cable/tile AUROC 仅 0.83-0.87（正常侧 CDF 校准粒度过粗、分数饱和 1.0 与缺陷侧平局），同流程 100 正常即恢复 0.96-1.0。**工业含义：新品类上线正常图应尽量 ≥50-100 张，20 张虽能跑通但排序质量明显受损**。【已修复】precheck 在 10-49 张区间追加警告（"少样本区 CDF 校准粒度较粗，AUROC 可能系统性低估约 0.1，建议补到 50 张以上"）。
3. **U62 虚高重估在真实验收流中自然触发且门控双向工作**：5 条误检反馈触发各槽位虚高检测，cable/tile/screw 各通过 1 次门控（drift 0.013-0.044 ≤ tol）完成 CDF 重估，bottle 被否决回滚（drift 0.175 > tol）——在线校准机制按设计运行。
4. **翻案率 0% 观察**：各品类 5 条错检反馈（多为误检 false_positive）后 flip_curve 无翻案。原因：反馈即学让 post 分数下降（虚高被抑制），但三态翻案判定要求 decision 翻转，anomaly→gray 不算翻案、且阈值由 fit 时正常分位数定死（算法侧 U69 已知遗留：fused 饱和下阈值重估不可用）。属预期行为边界，不影响验收结论。

- 翻案曲线在"误检抑制"场景下不敏感（分数降但 decision 不变即不翻案），如需呈现"误检率下降"叙事，可补分数降幅统计。

### gyudet 跨域学习增益专项（核心叙事证据）

### 重要发现（后续改进参考）

1. **MPDD 缺陷目录命名不统一**：tubes 是 `test/anomalous`，bracket_white 却是按缺陷类型分目录（`defective_painting`+`scratches`）。适配层对 mpdd 必须用 `defect_dirs="auto"`（test 下除正常目录外全收），写死 "anomalous" 会让 bracket_white 缺陷集为空。
2. **solder_smt FAIL 根因复核（纠正 6.19 发现 2 的归因）**：最初归因为"sanity 权重误导"，尝试加"锚定集自检回退"机制后发现两个事实：①用锚定集自检 sanity 权重是循环论证（权重本就由锚定集算出，自检必然 AUROC=1.0）；②正常侧融合均值恰为 0.50（CDF 校准按设计工作，非饱和失效）。**真因是 35 张正常图的少样本瓶颈**（M9 发现 2 已量化：20 张时 AUROC 系统性低估 ~0.1）叠加域差。已撤掉无依据的回退机制，solder_smt 作为"少样本+域差"真实边界如实记录（符合"不改代码凑过"原则）。工业含义：真实工业数据采集应尽量 ≥50 张正常图。
3. **gyudet 静态 0.71 高于 算法侧记录的 0.49-0.52**：算法侧 U38/U41 是 single/tiles9 旧口径，本系统 fast 工作点（sem/disc/shead + sanity）跨域起点更好；但 14 反馈增益 +0.064 弱于 算法侧 U46/U51 的 +0.10~+0.14——反馈数少（14 vs 53）是主因，且评估集只有 30 张 holdout，统计粒度 1/225。
4. **跨域场景 U62 虚高重估高频触发且门控双向工作**：gyudet 专项 14 条反馈触发 4 次重估（3 次通过 drift 0.011-0.032，1 次否决回滚 drift 0.072）；solder_smt/mpdd_bracket_white 各否决 1 次（drift 0.074/0.136）——在线校准机制在域差场景按设计运行，回滚路径真实生效。
5. **BTAD 锚定天然只有 2 张**（缺陷目录仅 ko 一个，2/目录 cap 规则下 anchors=2），btad_01/02 仍达验收线，说明少锚定鲁棒性可接受；MPDD tubes 同理（anomalous 单目录 anchors=2）。

### 遗留

- solder_smt 的"少样本+域差"双重瓶颈是真实边界（根因复核见发现 2），工业落地指引：正常图采集 ≥50 张；若后续要支持品类级 fusion 配置（如 solder_smt 用 equal），需引擎层加 per-category weight_mode 入口（当前全局配置）。

## 6.27 工单全流程 UI 走查（2026-08-29，`_wo1_fullflow_walk.py`）

**目标**：对工单「1」（挂 MPDD 数据源，6 品类）在真实 UI 上跑通全流程——选工单→工作台→准备模型（metal_plate）→评估→产线暂停/恢复+自动检测→错检反馈→学习提升→队列回队再检。**28 项断言全绿，QMessageBox 模态弹窗 0 次**。走查发现并修复 3 个真问题：

### 发现 1：engine_fast.yaml slots 结构错位（任何 fast profile 准备必失败）

- **症状**：metal_plate 准备任务报 `KeyError: 'shead'`（task failed）。
- **根因**：`configs/engine_fast.yaml` 中 `shead` 及 `blob/trad/layout/inp/open/tpl` 六个槽位配置被错误地放在 `augment:` 层级下（应为 `slots:` 下，与 sem/disc 同级）。`algo/factory.build()` 按 `s["shead"]["enabled"]` 访问直接 KeyError。
- **修复**：整块移回 `slots:` 下；加载后验证 `slots` 含全部 8 个槽位键、`augment` 只剩 pseudo/preprocess/enhance。
- **教训**：yaml 结构错位不报配置错误，直到运行时 KeyError 才暴露；改配置后应做键位断言。

### 发现 2：groups._pick 用 test/good 补正常图 → 违反数据隔离红线

- **症状**：修复发现 1 后准备 metal_plate 仍失败，`guard_bundle` 断言 `init_normal 含非 train 域样本（test/good）`。
- **根因**：`backend/core/groups.py` 的 `_pick` 设计"优先 train/valid，不足用其余 split（含 test）补齐"（为 MVTec 100+30 协议设计）。但 `algo/common/isolation.py` 红线：**init_normal 必须全为 train 域**（test/good 不得进 fit）。metal_plate 的 train/good 仅 54 张 < 数据源 pretrain_normal=100 → 用 test/good 补足 → 触发红线。MVTec 类品类（train/good ≥100）不触发，所以此前未暴露。
- **修复**：`_pick` 加 `allow_test` 参数——**normal 不补 test 域（宁缺勿滥），anomaly 允许 test 域**（红线对 init_defect 只限数量 ≤ 协议上限，不限域）。metal_plate 分组修正后 normal=54（全 train）、anomaly=30（test 缺陷）、detect=67，准备成功。
- **意义**：这是"数据源分组策略"与"数据隔离红线"两条规则的直接冲突，红线优先。设计文档 §3 的 MVTec 补足注释需同步修正（该策略对 normal 不再适用）。

### 发现 3：多品类工单下评估页无法运行（v3 移除顶栏品类下拉的回归）

- **症状**：评估看板点"运行评估"无效（无任务提交、进度条不出现）。

## 6.28 三页面（学习/监控/反馈）按 algo 实现走查（2026-08-29）

**动机**：用户发现学习曲线页①点回放会实质暂停产线但无提示②AUROC 恒为 1 与模型管理页数值不一致，要求按 algo 实际实现重新审视学习/监控/反馈三页。定位 2 个根因 + 3 个契约缺口，全部修复。

### 发现 1（根因）：回放全程持引擎写锁 → 产线实质停摆

- **链路**：`DetectionEngine.simulate_learning` 原实现从 load_snapshot 到模拟结束（数分钟）全程持 `_write_lock`；而产线消费循环（pipeline/service.py）每图 predict 都要经 `_ensure_loaded` 抢同一把锁 → 回放期间产线所有 predict 阻塞，UI 无任何提示。
- **修复**：锁范围缩小为只护 `current_version` 元信息读取；load 与模拟移出锁外。安全性依据：**快照版本目录不可变 + 回放用独立 pipe 副本**，与产线激活 pipe 无共享状态；CUDA 并发由 PyTorch 进程内序列化保证正确性（产线单图延迟可能因 GPU 抢占略升，属预期，UI 文案已说明"与产线并行、无需暂停"）。
- **教训**：引擎锁的持有范围必须按"保护什么状态"界定——只读不可变快照不需要锁；长任务持锁前必须追全部锁竞争方。

### 发现 2（根因）：AUROC 恒 1 是锚定集小样本饱和，非计算错误

- **口径核对**：学习曲线锚定集与模型管理「历史最佳验证 AUC」取样规则其实一致（test split 按 id anomaly/normal 各半），差异仅在样本量：n_eval=20（10+10）时 AUROC 分辨率 1/100，fast profile 下极易饱和恒 1.0；模型管理 accuracy 评估全量 test 不饱和。
- **修复**：默认 n_eval 20→60（schemas/evaluation service/api_client/UI spin 四处，30+30 分辨率 1/900），eval_every 2→5；曲线 hint 与参数 tooltip 写明"同取样规则、仅样本量不同，数值不必相等"。
- **同步修复**：`/learning/curve/{cat}/latest` 端点此前把 algo 早已返回的学习证据字段（a_recheck/intercept/weight_learn/thresh_recal/head_ft/disc_ft/box_supervised）全部丢弃——页面补 A 再检 KPI 卡 + 曲线下方学习证据行（拦截命中/权重通过否决/阈值重估/头与判别器微调计数），"学过就会"（A 再检）与"未见缺陷泛化"（锚定集）双指标互补呈现。

### 发现 3：algo 回放无进度回调 + 评估点双趟前向

- simulate_learning 原实现无进度上报（进度条只在开头 0/1、结尾 1/1 跳变），且每个评估点 AUROC/F1 分两趟 predict（成本翻倍）。
- 修复：加 `progress_cb`（按预估前向次数 total_fw 上报 done/total）；`_eval_full` 单趟同时出 AUROC/F1（评估点成本减半，符合单图 1s 红线下的总量控制）；`_intercept_stats` 支持复用末次锚定集 boost 省一趟前向。

### 发现 4：反馈页翻案曲线后台任务分支丢失（静默清空 + 潜在死循环）

- 契约：有 pre 的反馈数 >50（FLIP_CURVE_SYNC_MAX）时 GET flip_curve 返回 `{task_id}` 转后台，否则同步返回 points/summary。前端 `_fill_flip_curve` 原实现未识别 task_id → 曲线静默清空、KPI 显示 0、任务完成后不重载。
- 修复：task_id 分支显示"后台重打分中"进度；`_on_task` 监听 flip_curve 完成后**直接用 task.result 渲染**——不能再 reload_trace 重新 GET（反馈数仍 >50 会再次转后台，死循环）。**教训：转后台契约的端点，任务结果必须走 task.result 回填，重新请求就是重新排队。**

### 发现 5：监控页相机源漏 fast_mode 开关

- fast_mode 是会话级契约（ws.py 按 session 读取，视频/相机通用），视频源早有复选框，相机/RTSP 源漏暴露 → 补上并透传。其余字段契约（threshold/gray_threshold/weights/slots/defect_types/alarm/align_warn）逐项核对与后端 emit 一致，无漂移。

### 验证

9 个改动文件 py_compile 全过、六模块 import 冒烟全绿。速度红线（预估口径）：评估点前向次数减半；回放与产线并行只影响 GPU 抢占延迟，产线单图耗时不变。

### 补丁（用户确认后追加）：评估记录删除 + 噪声鲁棒性详情

- **评估记录删除**：后端新增 `DELETE /api/eval/runs/{run_id}`（admin 权限，同删批次门槛；仅删 EvalRun 记录行，不触碰快照/图片/模型，审计 `log_action(eval_run_delete)`）；评估页表格头部加「删除所选」按钮（勾选→确认→逐条删除→刷新）。此前评估记录只读不可删，误建/噪音记录无法清理。
- **噪声鲁棒性详情**：后端 `run_robustness_eval` 早已把各扰动类型分档 AUC + A_rob 算好落库（`metrics.curves`），UI 此前只显示 baseline_auroc 单值。补 `RobustnessDialog`：基线 AUROC + 各类型 A_rob 文本 + 分档 AUC 衰减折线图（LineChart 多系列），双击评估记录表格中的 robustness 行弹出。注意：不能改 x 轴为具体档位值是因为 EvalRun.metrics 未存 levels 档位数组（只有 auc_levels），用 1..n 档位下标展示，A_rob 语义在 hint 中说明。


## 6.29 监控页数据流视角重构（2026-08-29，"实时监控"名实对齐）

**动机**：用户指出监控页的"检测控制"（上传/库选/视频/相机四来源）本质是手动单图试检台，与产线数据流无关——页面名叫"实时监控"，却一帧都不显示产线（PipelineService）正在检的东西；仅有的"实时"来自页面临时起的 WS 监控会话，那是一条脱离工单/队列的影子产线，与产线消费机制重复冲突。

### 数据流定位

```
数据源(批次/RTSP/PLC) → 检测组队列 → PipelineService 消费 → detections 落库

```

algo §6 对"实时"的定义：检测单元永远是单图，"监控"的价值在**持续帧流 + 时序聚合**（EMA 平滑、短脉冲降级、滑窗连续异常告警）。页面据此重构为"产线流监视终端 + 操作员干预入口"。

### 变更清单

| 位置 | 变更 |
|---|---|
| `backend/pipeline/pipeline_service.py` | 产线消费/RTSP 流送检 target_type 改 `"pipeline"`/`"stream"`（原默认 "image" 与手动单图检测混流，无法区分数据流来源） |

- **移除**：MonitorWorker（QThread+websocket-client）、视频/相机 WS 会话面板、`_load_videos`。实时流归位到数据源（RTSP 源挂工单由 `_sync_rtsp` 统一消费），页面不再私启影子产线。
- **左栏**："检测控制"四来源收缩为「试检（旁路调试）」两个按钮（上传/库选），明示试检结果走 upload/image 通道、不进产线流与时序图。

### 踩坑与决策

1. **轮询而非 WS 推送**：产线节拍 ~0.5s/图、轮询是毫秒级 DB 查询，远低于 1s 红线；复用既有 REST，零新推送机制。若未来多客户端并发监控再升级 WS 广播。

## 6.36 引擎并发缺陷修复（2026-08-30，write_lock 阻塞 / predict 竞态）

**确认的两个缺陷**：

1. **_write_lock 阻塞所有品类检测**：旧实现 prepare()/consolidate() 把整个 pipe.fit()/save_snapshot（几十秒）包在全局 `_write_lock` 里，且 `_ensure_loaded()` 每次 predict 前都抢同一把锁 → 后台准备一个品类时，**所有品类**产线实时 predict 全部阻塞，违背"复判与检测并行、学完直接恢复不重启"。
2. **predict 并发安全**：`routes_detect._detect_lock` 只护 REST 同步接口，产线 daemon / RTSP 线程直接调 `svc.detect_image` 完全绕过 → `Pipeline.predict` 与 feedback 即学（改 NormalBank/融合权重）并发竞态；且该锁是全局锁，把不同品类也串行化。

**修复方案（engine/__init__.py）**：

- 品类级细粒度锁：`self._pipe_locks: dict[category, RLock]`（惰性创建，`_locks_guard` 护字典）。predict_image_path / predict_ndarray / submit_feedback / consolidate / active_suggestions / learning_insight / weight_history 全部持本品类锁 → 同品类 predict/feedback 串行安全，不同品类并行不互斥。锁序约定：品类锁/prepare 锁 → _write_lock，不可反向。
- `_ensure_loaded` 双重检查：锁外先查 `self._pipes`（dict 读原子），未命中才进 `_write_lock` 加载 → 已加载品类 predict 零抢锁。
- `prepare()`：build + fit + enable_ssocl（耗时部分）在 `_write_lock` 外；只有写快照/set_current_version/_pipes 替换在锁内。同品类并发 prepare 用 `self._prepare_locks` 防重——后到者在锁内幂等检查命中已激活版本直接返回，不重复 fit。
- `consolidate()`：`_ensure_loaded` 移出全局锁；save_snapshot 读 pipe 内存态须持**品类锁**（否则快照是 feedback 修改中的撕裂态），全局 `_write_lock` 只护版本号分配/指针切换。
- `routes_detect.py` 的全局 `_detect_lock` 删除（引擎品类锁已覆盖，且全局锁串行化所有品类）。
- **刻意不锁**：evaluate/contribution_report 是批量只读评估，整程持品类锁会把同品类产线 predict 阻塞分钟级（突破单图 1s 红线）；残留的单图级竞态与 predict×predict 同级，可接受。需严格一致时走 simulate_learning 独立快照副本路径。**残留风险**：`backend/evaluation/service.py` 的 A/B 与激活门控通过 `engine.get_pipeline()` 拿活 pipe 直接 predict，未走品类锁，后续如产线满负荷时跑评估需关注。

**冒烟验证**（fake algo 模块 + 多线程，已跑完删除脚本）：A 品类 prepare（fit 1.5s）期间 B 品类 4 线程 predict/feedback 单图最大耗时 659ms（无秒级阻塞）；同品类 pipe 最大并发=1；并发 prepare 同品类 fit 只执行 1 次且返回同版本；B/D 不同品类 predict 最大重叠=2（并行不互斥）。

  覆盖 TaskManager 全部终态（done/failed），新增任务状态枚举要同步前端。**
- **数据血缘核验（#4）**：模型匹配不再只凭品类名——precheck 带 datasource_id
  时对比 Model.metrics.dataset_ids（M16f 谱系）与该数据源批次集合，无交集
  提示"品类撞名"，部分重合提示"增补数据"。依赖 M16f 落库完整性：旧版本模型
  无 dataset_ids 时只能提示无法核验。

**业务模型（#7）**：

- 新建工单一律 pipeline_status=paused（此前列默认 running 导致投产即自动开线）。
  产线手动启停 + 顶栏产线状态徽标（10s 轻量轮询 get_workorder，带工单切换
  守卫）。auto_resume 逻辑保留（学习提升完成后恢复原运行态）。
