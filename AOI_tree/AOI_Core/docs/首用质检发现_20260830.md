# 首次使用者质检发现（2026-08-30）

> 场景：以"第一次使用"身份纯 UI 操作，用 MPDD 数据集完成全量检测的独立测评记录。
> 背景赛题：华为「可自学习的AOI实时在线AI质检」（2500×2500、<200ms、100正常+30缺陷迁移学习）。
> 本文为独立观察结论，未参考历史设计文档。供后续改进参考。

## 1. 使用路径回顾

导入 MPDD 1346 图 → 建工单挂数据源 → 6 品类逐个「准备模型」→「评估看板」验收 →「模型管理」激活 →「实时监控」恢复产线跑全量 →「标注反馈」→ 自动/手动学习提升。

## 2. 关键指标实测

| 指标 | 结果 |
|---|---|
| 模型准备耗时 | 9~16 s/品类（100 正常 + 30 异常，fast profile） |
| 验收精度 | AUROC 0.974~1.000、AP 0.983~1.000、F1 0.948~1.000，6/6 通过 |
| 全量检测 | 1346/1346 完成；准确率 84.5%（TP280/FP207/TN857/FN2） |
| 漏检 | 仅 2 张（tubes，score 0.73/0.86 低于阈值） |
| 误检 | 207 张，其中 158 张集中在 bracket_black train/good/2xx（score=2.0） |
| 检测延迟 | mean 162ms / p50 143ms / p95 311ms / max 533ms；超 200ms 占 36.3% |
| 对位预警 | 1240/1346（92.1%）帧触发对位偏移预警 |
| 灰区率 | 4.6%（62 帧） |
| 学习闭环 | 反馈(2条)→consumed→weight_history/online_curve 记录→6品类自动提升 v2/v3→手动巩固 v5 |

## 3. 阻断级 / 严重缺陷（须优先修复）

### B1 激活门控"鸡生蛋"：首次激活必失败（阻断）
`evaluate_activation_gate`（gate=true 默认开启）在首次激活时无当前版本可比，抛
`ValueError("品类 X 无激活版本，请先 /models/prepare")` → HTTP 400。
首次使用从"准备→验收→激活"的正常路径被完全切断。
**影响**：全新部署无法通过 UI 投产。临时绕过：API `activate?gate=false`。

### B2 快照孤儿治理误伤首用模型（阻断）
`register_demo5_snapshots` 用"有无 Detection 记录"判定血缘，首次使用无检测记录 →
把刚准备的模型标 `orphan=true`、note="历史残留（已切断激活）"、并**删除 current.json**，
激活指针被反复清空，UI 状态倒退（已验收→未验收）。

### B3 UI 对激活失败完全静默
点击「激活选中版本」后端 400，UI 无任何提示（无弹窗/无 toast/无日志条），
操作员无法感知失败，也不知道原因。

### B4 验收"✓ 通过"与实际延迟判定不一致
bracket_black 精度评估原始结果 `latency_pass=false`（首张 460ms、尾部分布超预算），
UI 却显示「✓ 通过」。验收通过逻辑与 200ms 延迟预算口径不一致，易误导上线决策。

## 4. 一般缺陷

- **B5 UI 不自动刷新**：API 激活成功后，模型管理页仍显示"未激活"；数据表格导入期间不刷新。
- **B6 检测队列混入训练集图**：产线流检测了 train/good 图（应只测 test/检测组），
  且 bracket_black train/good/2xx 整段被判异常 score=2.0（疑似该段图与训练分布差异大或阈值漂移）。
- **B7「学习提升」按钮点击无界面反馈**：仅通过 DB/API 观察到自动学习提升已执行。
- **B8 无障碍可访问性**：Qt 复选框不映射无障碍树（需 press_key 空格）；
  combo-box `set_value` 无效（需 expand 后点选项）。
- **B9 数据体检文案矛盾**：准备对话框显示"图库合计：异常 0 / 正常 0"，与实际预训练组 100/30 不符。
- **B10 统计页复核口径偏小**：复核覆盖率按"复核条数/检测数"（2/1346=0.1%），与"错检占比"口径并存，容易误读。

## 5. 正面发现

- 自学习闭环**真实运转**：检测过程中 6 品类自动生成 v2/v3 并激活（note="工单「MPDD全量检测」学习提升"）；
  手动巩固生成 bracket_black v5 并激活成功。
- 反馈"即学即用"：2 条反馈（确认正确+误检）写入后 `consumed=true`，`weight_history` 与 `online_curve` 有记录。
- 实时监控信息密度高：判定条带、异常率、评分依据面板、对位偏移、灰区、连续异常告警一应俱全。
- 全量检测漏检仅 2/1346，且在未逐帧复核下完成，工程可执行性良好。

## 6. 改进建议（按优先级）

1. 修复 B1/B2：首次激活跳过 A/B 门控；孤儿判定改用品类数据血缘（dataset_ids），并保留当前激活。
2. 修复 B3：前端统一捕获后端错误并弹窗/横幅提示。
3. 修复 B4：延迟验收与精度验收分开显示，口径与 200ms 预算严格对齐。
4. B6：产线队列仅消费 test/检测组；排查 bracket_black train/good/2xx 异常段（疑似版本/阈值问题）。
5. B5：页面数据变更后自动刷新或增加显式刷新提示。
6. 延迟优化：p95 311ms 超预算，建议分块并行或裁剪 backbone 以满足 <200ms 红线。

## 附录：延迟拆解与复判背压（2026-08-30 补充）

### A. 延迟拆解实测（6 张 anomaly 图，1024×1024，fast profile）

| 阶段 | mean ms | 占比 | 说明 |
|---|---|---|---|
| preprocess | 0.0 | - | 读图+resize |
| tile_cut | 0.0 | - | mode=single，1024² 仅 1 tile |
| **dino_extract** | **30.3** | 24% | DINO backbone 单次前向 |
| gpu_slot | 2.3 | 2% | sem/disc/shead 三槽 GPU 前向 |
| cpu_slot | 0.0 | - | fast 无 CPU 槽位 |
| open_det | 0.0 | - | 实测 no calls（注释"几乎零开销"正确） |
| intercept | 0.0 | - | 缺陷拦截通道 |
| **hier（含 defect_clf）** | **83.9** | **67%** | **热点**：h_mask 10.9 + h_boxes 1.2 + h_attr 70.6 |
| clf_feats | 0.4 | - | 图像侧特征（46维，已并行预取） |
| clf_proba | 23.5 | 19% | RF 300树 predict_proba（n_jobs=1 后） |
| **total** | **125.4** | 100% | 基线 157.9ms → 优化后 125.4ms（-21%） |

**关键结论**：
- defect_clf（U96 有监督类型判别器，RandomForest 300树）是最大热点，仅 decision≠normal 时触发。
- 纯 normal 图 min 57ms 已达标；整体 mean 162ms 高因评测工单 36% 是缺陷图（487/1346 anomaly avg 232ms）。
- 真实产线缺陷率 ~5% 时 mean≈60ms，与目标吻合。
- "小图应该更快"对 ViT 单 tile 不成立：1024² 仅 1 tile，DINO 前向 30ms 固定。

### B. 已实施的无风险优化（U113）

1. **RF predict n_jobs=1**：单样本 predict 无并行收益，joblib 调度开销 ~22ms/次（42→20ms，proba 数值 max diff 0.0）。
2. **图像侧特征与 DINO 前向并行**：`_img_features`（46维 HSV/geom/DoG）提交 `_cpu_exec` 线程池，与 GPU 前向重叠；`_attribute_types` 复用 future 结果。
3. **三路并行回退教训**：`_img_features` 内部三路（color/geom/dog）再并行实测 CPU 争抢，h_mask 10→25ms、total 116→119ms 反升，已回退为串行。

### C. 复判背压机制（前端反馈 v6-3）

**问题**：产线自动检测合理，但质检员复核速度跟不上时，待复核队列无限积压。

**方案**（不改表结构，复用现有字段）：
- `review_enabled=True` 的工单，PipelineService 每 tick 计算该工单名下待复核检测数（产线路径 + 无有效反馈）。
- **高水位暂停**：积压 ≥ `pipeline.review_backlog_high`（默认 30）→ 自动 `pipeline_status = "paused"`。
- **低水位恢复**：积压 ≤ `pipeline.review_backlog_low`（默认 10）→ 自动恢复 `running`。
- 阈值可在设置中心（`pipeline.review_backlog_high/low`）调整。
- 监控页显示「待复核 N 条 · 复判积压限流已启动（产线暂停送检）」。

**影响范围**：仅 review_enabled 工单；普通工单（review_enabled=False）不受影响。

## 附录：前端反馈 v7 修复（2026-08-30）

来源：`前端反馈.txt` L71-76 六问，逐项排查修复。

### v7-1 产线启动/暂停按钮行为不一致（已修）

- **根因 A（主因）**：复判背压自动恢复不区分暂停来源——人工点「暂停产线」后，只要待复核 ≤ 低水位，下一 tick 就被 `_apply_review_backpressure` 改回 running，表现为"暂停了还是运行中/按钮无效"。
- **修复**：背压自动暂停改用独立状态 `auto_paused`（pipeline_service.py），自动恢复只解除 `auto_paused`；人工暂停 `paused` 只能人工恢复（或学习提升按 auto_resume 恢复）。不改表结构（pipeline_status 本就是 String）。
- **根因 B（UI）**：两个按钮永远 enabled、不反映状态；请求在途可连点竞态。
- **修复**：监控页徽章区分「运行中/已暂停/自动暂停（复判积压限流）」，按钮随状态启停（运行中禁"暂停"以外的误操作），控制请求在途双禁、失败回拉真实状态（monitor_page.py）。

### v7-2 学习曲线回放很慢（已优化）

- **排查**：不是"没保存"——结果存 EvalRun 表，页面打开读 latest 不重算；慢在每次点「开始回放」全量重算，标准档（4 轮×25，锚定 60）约 **610 次完整 predict**。
- **三个叠加原因**：① `Pipeline.predict` 缓存命中也要先解码+预处理+切块（offline.py）；② `_item_cache` 128 条 FIFO < 回放图片总数（160+），锚定集特征每轮被挤出重算 DINO；③ 同一批图重复打分：每轮 AUROC/F1 分两趟，末次锚定集跑三趟（final AUROC、`_intercept_stats` 未复用 boost、U71 eval_ps），而单流版早有复用先例。
- **修复**（algo/eval/offline.py + algo/ssocl/learning_curve.py）：predict 命中缓存直接走打分；缓存上限改 `_item_cache_max` 属性、回放入口扩到覆盖轮池+锚定集；每轮 AUROC+F1 合并一趟 `_eval_full`；末次三趟合一趟并传 `eval_boosts` 给 `_intercept_stats`。预计省 40%+ 前向，且缓存命中路径不再付 DINO 代价。

### v7-3 监控页「伪异常判别」与检测延迟（排查，无需改码）

- 右侧「评分依据」面板的**伪异常判别 = shead 槽位分数**（image 模式），复用管线已提取的 tile 特征过一次 3 层 MLP，**零额外 DINO 前向**，约占 10-20ms，不是延迟主因。
- 389ms 尖峰主因：① 异常/灰区帧的归因分支（defect_clf RF 300 树 ~70ms+）；② 回放/评估等后台任务与产线共享 GPU 抢占。`total_latency_ms` 口径实测只含解码+推理（归档拷贝在其后），未虚高。
- 注意：shead 严禁在产线配置切 crop/guided 模式（会对每图滑窗重跑 DINO 1.5-3s，直接破 1s 红线）。

### v7-4 AOI_sys algo 与 demo5 行为不一致（已对齐）

- **排查结论**：核心算法代码 33/42 文件与 demo5 完全一致，其余多为 AOI 更新；**不一致在运行配置**——
  1. `SSOCL_CFG_TEMPLATE` 把 `head_ft/disc_ft` 阈值写成 9999（永不触发），而这两个分数级杠杆是 demo5"学习后 AUC 提升"的主力通道（代码默认 enabled=True 且阈值可达）；
  2. banks 缺 `intercept_sim` → 代码默认 0.85，但命中判据是相对差（分布仅 0.1~0.3）→ **缺陷样例拦截加分近乎失效**；`cluster_k=8/sim_thresh=0.85` 又使正常回流过严；
  3. 快照加载路径（persist.py tmp_cfg）同样硬编码 9999 锁死，且 pickle 的 bank 携带构建期旧参数；
  4. 多个死配置键（`thresh_recal.min_normals`、`weight_learner.*`、`active.top_ratio/max_queue`）代码根本不读。
- **修复**：`SSOCL_CFG_TEMPLATE` 与 persist.py tmp_cfg 全面对齐 demo5 m5（ext_max 64/cluster_k 3/sim_thresh 0.75/intercept_sim 0.15/intercept_boost 0.25；head_ft 20/40、disc_ft 60/120、thresh_recal min_n 20 均启用）；快照加载后用当前配置刷新 bank 可调参数（内容保留）。
- **已排除**：`assets/disc_pretrain.pt` 与 demo5 预训练头 MD5 一致（bd1c3061…）。
- **待验证**：对齐后需重跑一轮学习曲线回放确认增益恢复到 demo5 水平；fast（3 槽位）vs accuracy（全槽位）工作点差异仍在，demo5 成绩单出自全槽位精度模式。
- **注意**：demo5 m5 参数为评测调优值（如 intercept_sim=0.15），作为生产默认的合理性建议对照 demo5 消融记录（U24/U25/U105）持续观察。

> 背景：评审自检指出跨域（0.60→0.72）是唯一结构性天花板。demo5 侧早有"模板方式解决跨域"的设计（tpl 槽位 + mechH 实测 gold 1.0000 / solder 0.9932），但从未在系统链路（AOI_sys）验证过。本次在 UI 全链路验证"提供模板（L3）"数据条件。

### 8.3 算法效果：模板方案在系统链路不能复现 mechH 1.0000

系统链路（模板 8 张）实测：
- **tpl 单槽 AUROC = 0.1333（反向）**，sanity 加权把 tpl 权重置零（w_tpl=0.0），融合不受益
- 正常图 Image_*_repaired 全误报 anomaly（tpl 差分大：模板库不含它们的 repaired 配对）
- 部分缺陷图漏检（0604/0605/0607，其 repaired 配对不在模板库）
- **latency 3.3-7.1s 严重超 1s 红线**（tpl 像素差分通道：每模板 resize+torch 张量）

### 8.4 根因对照实验（`_verify_tpl_coverage.py`，TplSlot 直算，纯特征差分）

| 配置 | tpl 单槽 AUROC | 正常均值 / 缺陷均值 |
|------|---------------|--------------------|
| A：模板 8 张（t_fov 5 + train 3，=系统 limit） | **0.0333（反向）** | 3.67 / 2.07 |
| B：模板 85 张全库（68 train + 17 test repaired，=mechH 配置） | **1.0000** | 0.00 / 1.27 |

85 模板纯特征差分耗时 ≈ **235ms/图**（不含 DINO 提取），速度不是根本问题。

**核心结论**：
1. **模板覆盖度是决定性变量**：8 张模板覆盖不了 test 域正常样式分布 → tpl 反向；全库 85 张 → 1.0000。mechH 的 1.0000 本质依赖"模板库包含每张测试图的 repaired 配对"，是数据特殊性，不是通用方案。
2. **系统 prepare 模板收集上限 limit(8) 过小**（routes_models.py），是模板方案在系统链路的直接瓶颈。
3. **tpl 像素差分通道不可行**（每模板 resize + torch 张量，大图下 3-7s），应默认关闭（feat_w=1, pix_w=0）。
4. **tpl 无配准**：per-position 差分要求测试图与模板对位一致；gold_finger 对位偏移大（offset 最高 100+px），真实金样板场景需先配准。

### 8.5 改进方向（后续可选）

- P0：prepare 模板上限放开（8 → 50-100）或按正常样式聚类选代表模板；tpl 像素差分默认关。
- P1：tpl 增加配准（相位相关/特征点对齐）——与 M11d 对位预警复用同一能力。
- P2：PCB_Dual 的模板差分（金样板对位一致场景）验证 tpl 槽位接入双检融合。

### 8.6 诚实登记

- "模板解决跨域"在系统链路（8 张模板）下**不成立**（0.567/tpl 反向），仅在"全库配对模板"的特殊数据条件下成立（1.0）——后者在真实产线等价于每件产品都有独立金样板，不具一般性。
- 阴性结果如实记录，不做虚高包装；若 P0/P1 落地后再复测。

### 8.7 P0 落地：模板方案在系统链路转正（2026-08-30，同日续攻）

### 8.8 遗留边界全部解决（2026-08-30，同日收尾）

针对 8.7 的①②③三项遗留逐一落地并验证：

**① 模板覆盖依赖——量化确证 + 配准/学习组合兜底**
- 对照实验（TplSlot 直算）：模板=68 train（无 test 配对）AUROC **0.2667（反向）** vs 全库 85 **1.0000**。确证模板方案适用条件 = **模板库覆盖产线实际正常样式（金样板）**。
- 兜底：配准（②）+ 持续学习（正常图确认反馈回流校准/模板库）可在覆盖不足时自修复——"模板差分 + 持续学习"组合即为此设计。

**② tpl 配准落地（相位相关，P1 解决）**
- 实现（`algo/slots/tpl.py`）：逐模板相位相关响应 argmax 选"同产品参考模板"→ 求 (dx,dy) → **缩略(448)偏移放大回原图分辨率取负校正**（WARP_INVERSE_MAP 曾使方向反向，已去；BORDER_REPLICATE 防黑边）→ warp 后重提特征差分。默认开（`slots.tpl.align`，响应/偏移过小自动跳过）。
- 实测（测试正常图人工平移 50px）：配准后与原图相位相关偏移 **(0.04,0.0)≈0**、平均像素差 **19.35→1.58**；tpl raw diff 平移 2.58 → 配准后 **1.55**（降低 40%，剩余为双线性插值残差，配合在线学习收敛）。
- 配对场景（offset≈0）自动跳过配准，**系统链路 17/17 保持 AUROC 1.0**，latency p50=484ms（相位相关扫描 85 模板 +250ms，仍 <1s 红线）。

**③ 决策闸门小缺陷保护（heatmap max 判断）**
- 实现（`algo/eval/offline.py`）：tpl 闸门从"topk 均值 <1.0"收紧为"**tpl 热力图最大 patch 差分 < 校准 ref**"——topk 均值会被 ≤10% 面积缺陷稀释，热力图 max 保留单个显著异常 patch 的检出，避免小缺陷被误压为 normal。
- 系统链路 17/17 保持 AUROC 1.0 验证通过。

**最终状态（2026-08-30 收尾）**：gold_finger L3 全库模板差分在系统链路 **AUROC 1.0000、判定 17/17、latency p50=484ms**；配准/闸门/校准三项工程改进全部落地且不破坏既有成绩；剩余边界为**数据条件要求**（模板库需覆盖产线正常样式）与插值残差（靠在线学习收敛），均已如实登记。
