# 前端问题解答

## 结论摘要

| 问题 | 结论 | 本次处理 |
| --- | --- | --- |
| 每个页面是否都要显示数据条件 | 不需要。数据条件是当前工单的上下文，不是页面自身的属性。 | 保留主窗口顶部统一显示，并随工单切换刷新；移除各页面顶部重复徽标。 |
| 顶部“产线”是什么意思 | 当前工单绑定的检测管线运行状态，不是物理产线名称。 | 补充悬停说明，明确它只影响当前工单的实时检测消费。 |
| 角色有什么作用，如何切换 | 角色是后端权限等级：操作员 < 工程师 < 管理员。角色来自 X-API-Key 映射，不是页面内下拉选项。 | 补充角色徽标说明，避免用户误以为可以在 UI 直接切换。 |
| 系统设置配置文件路径是否写死 | 不是完全写死。后端优先读取 `AOI_CONFIG` 环境变量；未设置时才使用项目 `configs/default.yaml`。 | 设置页明确展示当前后端实际路径，并补充路径来源和生效方式。 |

## 1. 数据条件是否需要每个页面都显示

不需要每页重复显示。

数据条件描述的是**当前工单所声明、并由数据源体检校正的数据能力**，例如“仅正常图”“图像级标注”“缺陷位置标注”，还可以叠加“品类独立”“模板比对”。它会影响建模方式、数据导入、评估口径和统计解释，因此属于当前工单的全局上下文。

当前正确关系是：

```text
切换当前工单
    -> 当前工单的数据条件变化
    -> 顶部统一徽标刷新
    -> 各页面按同一工单条件重新加载/计算
```

因此，顶部显示一次即可。页面内重复显示会占用有限的横向空间，也容易让用户误以为每个页面可以单独设置一套数据条件。工作台表格中的“数据条件”列仍然保留，因为它是工单列表中的业务字段，可用于比较和双击编辑，不属于页面标题重复展示。

## 2. 顶部“产线”的含义和作用

顶部的“产线”是**当前工单的检测管线状态**，取值主要包括：

- 运行中：管线会消费当前工单的数据流并执行实时检测；
- 已暂停：暂时停止送检，复判、学习、数据编排等操作不等同于删除；
- 自动暂停：通常表示复判积压触发了限流；
- 已停止：管线停止，恢复需要人工操作。

它与“实时监控”页直接相关：实时监控页负责查看检测流、队列、复判积压，并执行暂停、恢复、停止。数据管理页的批次回队/编排会影响管线可消费的数据，标注反馈页的复判积压也可能触发自动暂停；但“产线”本身不是系统设置里的一个普通文本名称，也不是电脑连接的物理生产线名称。

顶部徽标只做全局状态提示，真正的启停操作应在“实时监控”页完成。状态跟随当前工单切换，并由后台定时轻量刷新。

## 3. 角色的作用、切换方式和差异

系统支持三类角色，权限从低到高为：

| 角色 | 主要用途 | 页面/操作差异 |
| --- | --- | --- |
| 操作员 `operator` | 日常产线操作 | 主要看到工作台、实时监控、标注反馈、存档统计；不能进行模型、数据配置和系统管理操作。 |
| 工程师 `engineer` | 数据、模型和质量维护 | 可访问准备期、评估、学习等工程页面，并执行工程操作；管理员专属操作仍不可用。 |
| 管理员 `admin` | 系统和生产管理 | 全部页面和管理操作，包括配置保存、候选激活/回滚、系统清理等高风险操作。 |

角色不是在前端页面里临时切换的筛选项。后端根据请求头 `X-API-Key` 将密钥映射为角色；鉴权关闭的开发模式默认按 `admin` 处理。因此切换角色的正确方式是：

1. 在后端安全配置中为不同 API Key 配置角色映射；
2. 让客户端使用目标角色的 API Key；
3. 重新连接/重启客户端，使新的 `system/info` 返回角色并刷新导航权限。

仅隐藏导航不是安全边界，后端接口仍会通过 `require_role` 再次校验权限。也就是说，角色切换后不仅页面可见范围不同，实际 API 操作权限也不同。

## 4. 系统设置里的配置文件路径

配置路径由后端 `Settings` 决定：

1. 优先使用环境变量 `AOI_CONFIG` 指定的文件；
2. 未设置 `AOI_CONFIG` 时，使用项目内的 `configs/default.yaml`。

设置页的“配置文件”文本是后端返回的实际 `config_path`，不是前端写死的路径。白名单配置项保存时会写回当前配置文件并热生效；引擎内部参数、安全密钥等高风险项仍不通过页面开放。

如果要切换配置文件，应在启动后端前设置 `AOI_CONFIG`，例如：

```powershell
$env:AOI_CONFIG = "D:\deploy\aoi\production.yaml"
```

修改配置文件路径后需要重启后端，客户端刷新页面不能改变已经运行的后端配置来源。

## 5. 模拟系统的统计范围与工单耗时趋势

### 为什么工作台不再提供时间范围下拉

模拟系统默认统计**当前工单全部已落库检测记录**，不再按今日、近 7 天等时间窗口裁切。时间戳用于追溯检测和反馈发生的时间，不用于限定当前工单的默认统计范围。未选择工单时仍使用全局口径，并保留排除已存档工单的规则。

工单归属以检测记录的 `Detection.workorder_id` 为准，不以品类或数据源覆盖范围推断。两个工单即使使用同一品类，也不能互相计入；未写入工单 ID 的历史记录不能通过品类自动认领。待复核计数也按真实工单归属计算，旧后端缺少工单计数字段时显示不可用，不使用品类计数近似。

### 为什么原来的近 30 天日聚合需要替换

原耗时图读取按日期、品类汇总的日聚合数据，不能严格区分同品类的不同工单，而且固定近 30 天会漏掉更早的工单记录。因此存档统计改为读取当前选中工单的真实检测记录：

- 全部检测都有导入批次时，按批次聚合平均推理耗时，并按各批次首次检测的顺序排列。
- 只要存在没有批次归属的检测，就改为全部记录按检测 ID 顺序展示，避免漏掉上传或数据流检测。
- 存档工单可以单独查看；工单不存在或没有检测时返回空数据，不能回退到其他工单或全局统计。
- 切换工单后丢弃旧工单请求的回调，避免异步响应覆盖新工单的图表。

### 产线健康与缺失数据如何处理

存档统计的产线健康同步改为 `all`，扫描当前工单全部检测，不再固定近 7 天，也不再截取最近 3000 条。总览、质量、缺陷类型、批次对比和误判趋势同样遵守工单隔离与全部范围；误判趋势仍按实际反馈日期追溯，包含全部历史日期。

耗时图展示的是模型推理耗时，不把它伪装成端到端耗时。缺失耗时不补零、不插值；无数据时保持空态，缺失点断线；批次均值仅计算有真实推理耗时的记录。无复核分母的比率、缺失端到端耗时继续显示“—”或不可用。

工单列表保留原有人工复判工单按已复核记录计算的业务规则；统计页总览的检测数则是该工单全部落库检测。这两种分母不能混为一谈。

## 6. 工作台指标文案调整

### 6.1 指标含义与计算方式

- **检测数**：当前工单已保存的 `Detection` 记录数。它统计的是检测结果记录，不是相机接收帧数；同一图片重复检测会产生多条记录。
- **不良数**：`Detection.is_anomaly=True` 的记录数，即系统最终判定为异常的数量。`decision="gray"` 的灰区结果不计入不良数，而进入待复核流程。
- **不良率**：不良数 ÷ 检测数。没有检测记录时分母不存在，界面显示“—”，不伪造 0%。这是系统判定比例，不等同于复核后的真实不良率。
- **待复核**：当前仍等待人工裁定的检测记录数。普通灰区记录会进入队列；启用人工复判的工单还可能把其他检测结果纳入队列，已提交有效反馈的记录不再计入。
- **模型判断耗时（均值）**：`Detection.latency_ms` 的平均值，表示模型完成一次判断的耗时，不含相机采集、传输和结果保存。
- **检测处理耗时（均值）**：`Detection.latency_e2e_ms` 的平均值。后端从检测处理开始计时，到保存前完成解码/推理/同步热图处理；不含落库和告警，也不代表相机到保存的完整链路。字段缺失的记录不参与平均，并单独显示缺失数量。
- **接收后保存比例**：理论上是“接收数量中成功保存检测结果的数量 ÷ 接收数量”。当前接口没有独立的接收计数器，只有保存后的记录，无法反推出分母，因此显示“不可用”，不代表 0%。这不是要求必须连接相机，而是当前统计数据源不足。

### 6.2 P95 是否应出现在成品 UI

`P95` 是第 95 百分位：将样本耗时从小到大排序后，约 95% 的样本不超过该值。它是通用性能统计术语，不是测试代号，也不是只能用于测试的字段。为了让演示系统的主界面更易懂，本次主卡片只显示均值；P95 仍可在工程详情、性能报告或后续“详细指标”区域展示，并可标注“95% 样本不超过”。

### 6.3 口径说明改为用户语言

原来的“口径：窗口……分母……”属于内部统计实现语言，已改为：

> 统计对象：当前工单｜共 N 条已保存检测结果｜来源：产线 N 条、上传 N 条……

这样用户可以直接知道统计的是哪个工单、共有多少条结果以及结果来自哪里；日期仅用于追溯，不再作为模拟系统的默认统计范围。原来的“窗口”“分母”“persisted_detections”等内部字段名不再直接展示。

## 7. 工单、产线对接与数据管理说明

### 7.1 工作台工单统计表

工作台表格当前是“工单统计汇总”，不是完整的工单生命周期看板。各列含义如下：

| 列 | 含义 |
| --- | --- |
| 工单 | 工单名称；单击行可切换当前工单 |
| 数据条件 | 工单声明的标注、品类独立、模板等检测条件 |
| 数据源 | 工单挂接的数据源 |
| 品类 | 数据源中实际存在的品类 |
| 图片数 | 数据源中的图片总数，不等于待检测数 |
| 体检 | 工单声明条件与数据实际能力是否匹配 |
| 检测 | 已保存的检测结果数，不代表全部图片已完成检测 |
| 不良 | 系统判定为异常的检测结果数 |
| 不良率 | 不良数 ÷ 检测数；没有检测记录时不计算 |

工单表现在增加了可执行状态摘要：未开始（无检测记录且无在途任务）、进行中（存在运行中管线或在途任务）、已完成（当前工单已无可检测图片且无在途任务）、已暂停/已停止，以及已关闭/已存档。该摘要由工单状态、管线状态和当前工单队列共同计算，不把单一字段误当成完整状态。

### 7.2 工单机制、生命周期与队列

工单用于把一组数据源、检测条件、检测结果和人工复核归到同一个生产任务中。当前流程是：

```text
先建立并导入数据源
  → 创建工单并挂接至少一个数据源
  → 体检数据条件并准备模型
  → 启动/暂停/停止检测管线
  → 产生检测结果与复核任务
  → 队列耗尽后显示已完成
  → 关闭或存档工单并停止后续消费
```

关闭、存档或停止工单时会停止关联管线、释放在途图片认领，并拒绝旧 worker 的迟到结果写入；关闭或存档工单不能再次恢复。`pipeline_status` 表示产线运行状态，`archived` 表示数据归档状态，工单摘要则综合两者和队列状态。删除工单仍会级联删除相关检测和反馈，不能用存档代替删除。

队列是当前工单对本地图片的检测安排：从工单挂接的数据源找到批次和图片，逐张认领、检测、保存；错检批次可以回队，回队图片优先重检。回队不会创建新的数据库批次。RTSP 实时流按视频帧处理，不使用本地图片批次队列。

### 7.3 新建工单需要什么

当前 UI 创建工单的必填内容是：

- **工单名称**：用于识别、切换和归属统计。
- **至少一个数据源**：没有数据源就没有正常的检测数据和队列。

可选内容包括：

- **人工复判**：开启后检测结果进入人工复核流程。
- **备注**：保存业务说明或准备提醒。
- **复制工单配置 / 保存为任务模板**：复用数据源挂接和复判设置。

标注档位、品类集合、模板能力、图片数和检测批次不是工单中独立手填的，它们主要由数据源声明和实际数据自动聚合。当前界面不允许创建空工单；但后端接口对空数据源列表的限制并不完整，因此 API 产生的无数据源工单应视为不完整配置。

### 7.4 产线对接能力

工作台这一区域是配置能力摘要，不是实时通信诊断面板：

- **Webhook 告警**：检测/告警事件通过 HTTP 推送到 MES 或上位机。当前实际事件包括异常、灰区、开放集、对位预警和连续异常告警；只有配置地址且订阅对应事件时才发送。发送失败记录日志，不会回滚检测。
- **PLC 触发**：AOI 不直接监听 Modbus、OPC UA 等 PLC 协议。外部 PLC/光电系统触发相机落图，上位机或 MES 调用 `POST /api/detect/trigger`，AOI 从触发目录按文件时间取最早的一张，检测后移到 `processed/`。
- **自动归档**：按配置把异常或灰区原图/视频帧复制到 `storage/archive/品类/日期/`，并登记为 `split=archive` 的数据批次。数据库检测记录仍保留。它用于证据追溯、质量复盘和训练回流，不会未经复核自动进入生产训练集；可在数据管理中查看，确认并重新划分后再用于训练。
- **API 鉴权**：外部访问 `/api/*` 等受保护路径时携带 `X-API-Key`。认证失败是 401，角色不足是 403。角色等级是 `operator < engineer < admin`，工作台顶部角色来自同一套后端身份，不是单独的前端开关。

把这些能力放在工作台，是因为它们影响“当前工单能否接收数据、如何触发检测、是否留存证据以及外部系统能否调用”；具体配置仍在系统设置或安全配置中完成。

### 7.5 数据源与工单的先后顺序

推荐顺序是：

```text
先新建数据源并导入/归属数据
  → 再创建工单并挂接数据源
  → 检查数据能力与划分
  → 运行检测队列或实时流
```

数据源是可复用的数据入口和能力声明；同一个数据源可以被多个工单挂接。工单则是一次检测任务的组织和统计上下文。

## 8. 数据源、数据导航、批次与队列

### 8.1 API 鉴权与工作台角色的关系

API 鉴权用于保护外部接口和管理操作，不是日常页面筛选。启用后，调用方需要在请求中携带 `X-API-Key`；系统先验证密钥身份，再根据密钥映射的角色决定接口是否允许执行。认证失败返回 401，密钥有效但角色权限不足返回 403。

工作台上方的角色就是当前客户端这套 API Key 在后端解析出的角色，二者是同一身份来源：

```text
X-API-Key → 后端认证 → operator / engineer / admin → 导航显示与接口权限
```

角色不是在工作台上临时切换的按钮。开发模式未配置密钥时默认按管理员处理；生产或非回环部署应配置密钥。页面隐藏按钮只是用户体验，真正的安全边界是后端路由的角色校验。

### 8.2 应先建数据源还是工单

应先建立并准备数据源，再创建工单：

```text
新建数据源 → 导入/归属批次 → 检查数据能力与分组 → 创建工单挂接数据源
```

当前界面创建工单时要求至少选择一个数据源。这样设计是因为工单的检测条件、品类、可用图片和队列都依赖数据源；工单不是孤立的空容器。一个数据源可以被多个工单复用，工单只决定本次任务如何组织、检测和统计。

### 8.3 新建数据源要填什么，为什么

数据源登记的是“数据从哪里来、具备什么能力、如何组织和如何送检”，不是简单给文件夹起名字。主要信息如下：

| 信息 | 作用 |
| --- | --- |
| 名称 | 在数据管理和工单挂接时识别数据源 |
| 模态 | 区分图片和视频，决定导入及处理方式 |
| 源类型 | 本地目录、RTSP 实时流或视频文件模拟流，决定数据如何进入检测 |
| 标注档位 | 声明当前数据能支持的模型准备方式；导入后会体检并校正 |
| 品类独立 | 表示是否按品类组织数据，影响工单条件和模型准备 |
| 模板图 | 声明是否提供模板比对所需的模板图片 |
| 预训练正常/异常图数 | 每个品类从训练/验证数据中选多少图片进入预训练组 |
| 检测批次图数 | 把剩余检测图片按多少张切组，便于队列消费和错检回队 |
| 采样/流配置 | 控制视频抽帧、RTSP 地址、流品类和循环方式 |
| 数据导入信息 | 指定导入文件夹、MVTec 或视频及批次名称，把实际文件登记到数据源 |

这些字段体现的数据源业务逻辑是：先把原始数据登记为一个可复用的数据入口，再通过“标注能力 + 品类/模板能力 + 分组规则”生成可供模型准备和产线检测使用的数据视图。数据源删除时，其关联批次和图片也会被清理，因此删除前应确认没有其他工单需要复用。

### 8.4 数据导航为什么是“数据源→品类→批次→用途划分→标签”

这套层级同时对应数据的来源、业务维度、物理归属、用途和标注：

```text
数据源
  → 品类
    → Dataset 批次
      → 用途划分：预训练组 / 检测组 / 导入数据的 train、valid、test 等
        → 标签：正常、异常、缺陷类型等
```

- **数据源**回答“数据从哪里来、是否可被多个工单复用”。
- **品类**回答“检测的是哪类产品或部件”，模型通常按品类准备。
- **批次**回答“这一组图片由哪次导入、视频抽帧或自动归档产生”。
- **用途划分**回答“图片用于预训练、检测、验证还是归档”，避免训练数据与检测数据混用。
- **标签**回答“图片当前被标记为什么”，用于统计、训练筛选和复核。

这样管理比把所有图片平铺在一起更容易追溯来源、选择训练样本、按品类准备模型，也能让工单只消费自己挂接数据源下的数据。

### 8.5 批次是什么，如何产生，有什么作用

批次对应数据库中的 `Dataset`，是图片、视频或视频帧的来源归属容器，不等同于右侧“划分”计算出的检测图片组。

批次主要由以下操作产生：

- 导入文件夹时创建一个文件夹批次；
- 导入 MVTec 时通常按品类创建批次；
- 注册视频并抽帧时，视频和帧归属于对应批次；
- 自动归档异常/灰区时，按品类和日期创建或复用“自动归档”批次。

批次的作用是保存来源路径、导入时间、品类、图片数量和数据源归属，让图片能够被查询、统计、训练筛选和检测消费。删除数据源会清理其关联批次和图片；批次本身也可以先创建后再挂接数据源。

### 8.6 “划分”是什么意思

右侧数据属性中的“划分”是对数据源内图片的用途分组，不是创建新批次。系统按每个品类的配置动态计算：

```text
可用图片
  ├─ 预训练组：从 train/valid 中选指定数量的正常图和异常图
  └─ 检测组：剩余可检测图片，按“检测批次图数”切成多个图片组
```

模板图不会进入预训练组或检测组。保存分组方案时，主要固定预训练图片 ID；检测组仍会根据当前数据和配置动态计算。因此“划分”是模型准备和检测编排的视图，不是新的 `Dataset` 记录。

### 8.7 批次和队列是什么关系

二者不是同一个对象：

- **批次**是数据的来源容器，说明图片属于哪次导入或归档；
- **检测组**是按配置从图片中动态切出的图片 ID 子组；
- **队列**是当前工单的运行时检测安排，决定哪些图片现在送检、重检或等待。

本地图片检测通常按“当前工单 → 挂接数据源 → 数据源下批次 → 图片状态和检测记录”逐张消费。RTSP 则按实时视频帧处理，不依赖本地图片批次队列。错检回队写入工单的运行时队列信息，回队图片优先重检，不会新建 Dataset 批次。

### 8.8 数据流队列的机制和作用

数据流队列不是简单的待办列表，主要承担以下职责：

1. 按当前工单逐张选择本地图片送检，而不是一次性处理全部数据；
2. 通过图片认领状态和 `claim_token` 防止多个 worker 重复检测同一张图片；
3. 记录成功、失败、重试次数和错误信息；
4. 支持错检批次回队，回队任务优先于普通检测；
5. 当人工复判积压达到高水位时自动暂停产线，积压下降后再恢复；
6. 将本地图片队列与 RTSP 实时流这两种检测入口区分开。

因此用户在数据管理页看到的队列表格，是“当前工单如何消费和重检数据”的运行视图，不是另一套数据存储，也不代表工单已经完成或未完成。

## 9. 数据增强页面

数据增强页属于“准备期”，作用是为下一次“准备模型”配置训练数据如何扩展和统一处理；它不是产线实时处理页，也不是把所有增强结果永久批量导出的文件管理器。当前页面分为三部分：左侧选择正常基底图，中间配置，右侧做单张伪异常预览。

### 9.1 左侧基底图从哪里来

左侧只加载已经登记到数据库中的 `label=normal` 图片，并按“数据源 → 品类 → 批次 → 图片”展示。它使用数据管理页已经导入的数据，不会在这里创建数据源或批次。选择正常图只是为了预览和作为模型准备时的正常样本来源；没有正常样本时，应该先回数据管理页导入。

### 9.2 页面上的三类配置

| 配置 | 作用 | 何时生效 |
| --- | --- | --- |
| 伪异常合成 | 在正常图上合成训练用异常信号，包括真实缺陷移植、CutPaste、色斑；每张基底图的生成数量由“每图伪异常数”控制 | 下一次准备模型时由引擎按需生成，不把训练用伪异常作为普通图片批量落库 |
| 图像预处理 | 统一训练和检测两侧的图像口径，可配置灰度、CLAHE 对比度增强和中值去噪 | 下一次准备模型及后续检测使用同一配置 |
| 训练增强 | 只对正常基底增加水平翻转、90°旋转、亮度/对比度变化，扩展正常外观变化 | 下一次准备模型时增加正常训练变体 |

“伪异常合成”与“训练增强”不是同一件事：前者制造模型要学习识别的异常信号，后者扩展正常样本的外观变化，目的是减少轻微位置和光照变化造成的误报。

### 9.3 伪异常方式和回退逻辑

- **真实缺陷移植**：只使用同品类、带有效缺陷位置标注的缺陷图作为移植源，把缺陷区域随机缩放、翻转并贴到正常图上。
- **CutPaste**：从图内裁一块，再变换后贴回其他位置，制造结构不连续。
- **色斑**：在局部区域做颜色或亮度偏移，模拟外观变化类异常。
- 如果选择真实缺陷移植，但当前品类没有有效位置标注，系统从可用方法中移除移植；仍有其他方法时从中选择，无其他方法才回退 CutPaste。不会把一张没有缺陷区域标注的整图当作“缺陷块”移植。

每图生成数量越大，训练样本和准备时间越多，但不代表真实缺陷数量增加，也不等于已经发现了新的生产缺陷。伪异常只用于模型学习，不能直接作为不良统计或人工复核结果。

### 9.4 预览和保存的边界

右侧“预览合成”是单张同步预览，会生成预览图和掩码文件供界面显示，但不会登记为正式数据集，也不会自动进入训练集。中间“保存配置”只写回当前引擎基础配置，接口要求工程师权限；保存后需要下一次“准备模型”才使用新配置。页面不负责启动训练，训练仍由模型管理页的“准备模型”触发。

### 9.5 与数据管理、模型管理的关系

```text
数据管理导入正常/缺陷/模板数据
  → 数据增强配置伪异常、预处理和训练增强
  → 模型管理“准备模型”按数据源预训练组取样
  → 引擎训练时按配置生成训练变体
  → 生成并验收模型后，工单检测使用统一预处理
```

数据增强不会改变数据管理页原始批次的归属，也不会自动把增强结果加入生产检测队列。真正的训练样本范围仍由数据源的预训练组/检测组和模型准备流程决定；模板图用于模板场景，不会因为打开数据增强就自动变成训练样本。

### 9.6 伪异常、基底图与“排除错误特征”

**基底图**就是作为合成底板的图片；本页左侧只提供已登记的正常图，预览不会覆盖原图。模型准备阶段还会按训练流程切成图块，因此页面整图预览是外观检查，不是最终训练图块的逐项重现。

伪异常是在图像上人工制造异常外观，为少缺陷样本场景提供额外监督信号。当前实现先提取特征，再训练 disc 小判别头：正常特征标为 0，合成图特征标为 1，以二分类损失学习异常输出。特征提取骨干冻结，**不会通过这项训练把正常向量收拢、将异常向量推远，也没有自动剔除“错误特征”的操作**。更准确的理解是“用合成例子帮助判别头学习什么外观应判异常”，不是“保证学到所有真实缺陷”。此配置只影响启用的 disc 判别分支，并不意味着其他正常记忆库、传统特征等分支都会同步得到同样训练。

还要注意当前训练限制：合成图的所有 patch 特征都作为异常正样本，合成掩码没有用于逐 patch 区分正常背景与缺陷区域。因此不能声称模型已经实现了精确的缺陷区域监督；不合理的合成也可能引入噪声和误报。

### 9.7 各选项的原理、作用与风险

| 选项 | 实际机制 | 主要用途与风险 |
| --- | --- | --- |
| 真实缺陷移植 | 从同品类带位置掩码的图中抠出缺陷，随机翻转、缩放、贴入 | 扩展少量缺陷形态；位置或尺寸不符合实际时可能学到拼贴假影 |
| CutPaste | 从基底裁块、随机翻转并贴到另一位置 | 制造局部结构不连续；不能代替真实缺陷验证 |
| 色斑 | 对椭圆区域做颜色乘性变化 | 模拟局部颜色变化；可能把正常反光、光照变化当成缺陷 |
| 每图伪异常数 | 对每个训练基底图块合成指定数量的变体 | 增大训练量和准备耗时，数量多不保证更准确；0 表示不生成这部分合成变体，并非关闭全部检测分支 |
| 缺陷块缩放 | 当前算法固定将缺陷块长边缩放到基底短边的 10%～40%，保持纵横比 | 原页面可编辑范围未被算法读取；现已禁用并显示实际固定规则，不把无效参数假装成有效控制 |
| 边缘羽化 | 真实缺陷移植时平滑混合边缘 | 减少硬边拼贴，但可能削弱细小缺陷；不控制 CutPaste 和色斑 |
| 启用预处理 | 预处理总开关，关闭则原样通过 | 训练和检测应保持同一口径；改动后重新准备、验收模型 |
| 灰度化 | 去除颜色信息，复制为三通道供模型输入 | 减少无关颜色差异，但会丢失色差、氧化、变色等判别线索 |
| CLAHE | 在亮度通道做限制对比度的局部直方图均衡；0 关闭 | 可能改善光照不均和弱纹理，也可能放大噪声或正常纹理；数值不是准确率提升百分比 |
| 中值 3×3 / 5×5 | 用邻域中值替换像素，抑制孤立噪点 | 大核更平滑，也更容易抹掉细划痕、针孔等真实小缺陷 |
| 水平翻转 | 给正常样本增加镜像变体 | 仅适用于左右翻转仍正常的对象；方向、文字、装配位置有意义时可能有害 |
| 旋转 90° | 增加正常样本的直角旋转变体 | 仅适用于该方向变化允许的品类；可能削弱错向检测能力 |
| 亮度 / 对比度扰动 | 对正常图做随机亮度和对比度变换 | 扩展正常光照容忍度，也可能掩盖需要检测的亮度异常 |

多选伪异常方式时，每次合成随机选择一种，并非每种都生成指定数量。全部不选时当前会使用 CutPaste 兜底；不是关闭伪异常。没有有效缺陷位置标注时，移植方式会从可用集合中移除；若仍选择其他方式则从剩余方式合成，集合为空才回退 CutPaste。

### 9.8 如何判断配置对检测是正面还是负面

当前数据增强页已提供「真实特征空间分析」弹窗，并新增一键增强消融评估入口：固定小样本 train/test 或 holdout，分别拟合基线与关闭单因素增强的配置，真实计算指标和差值并持久化 EvalRun。它仍是单种子趋势比较，不代表生产收益或统计显著性；图像预览和三维散点本身不能证明检测更好。

系统已有评估看板的精度、延迟、噪声鲁棒性评估和两条评估记录对比，可用于人工对照：

1. 固定品类、互不混用的训练/验证/测试样本及抽样清单，测试集中同时保留真实正常图和真实缺陷图；不要用合成异常本身证明真实缺陷效果。
2. 保存基线版本与配置，记录评估指标；只改变一类增强参数，重新准备候选模型。
3. 使用相同测试图片和一致的阈值/误报预算比较误报率、检出率、AUROC/AP、延迟；分别检查细小缺陷、颜色缺陷及不同来源的数据。通用精度评估中的 F1/混淆矩阵采用最优 F1 阈值，并不等于当前生产阈值的在线表现。
4. 误报下降但漏检上升，或者总体变好但关键缺陷变差，都不能简单判定为收益。小样本结果还需考虑随机性，不能仅凭一次分数差异作保证。

现有模型版本 A/B 后端可进行同集比较，但评估页对 A/B 嵌套结果的专门展示尚不完整，不能描述为完整的增强配置自动验证闭环。本轮没有实际训练两份模型，因此**没有可报告的提升百分比或正负效果结论**。

### 9.9 三维向量演示能说明什么

数据增强页右侧「真实特征空间分析」打开独立可旋转、缩放、点选的三维弹窗。先在左侧选择正常图；以第一张选图确定品类，优先限定其批次所属数据源，无数据源时限定该批次。未指定批次时展示同品类范围，弹窗明确标出。使用当前未保存的伪异常/预处理配置，默认每类最多8张、上限12张，固定随机种子20261015；每类仅查询ID排序前120条候选后抽样，不扫描全库图像。真实正常/真实缺陷排除伪异常、增强来源及相应批次。无真实缺陷可运行但明确缺失，不伪造第三类；需至少3张独立内容正常参考。

这不是disc深度向量：局部实例调用200维传统提取器，不加载DINO、不执行模型前向、不修改训练算法或生产引擎。图像检查尺寸后缩至最长边512，并统一成方形以适配现有合成器；256px提取预计每图<500ms，显示160px内存PNG缩略图。极端尺寸/宽高比被拒绝，缩图及方形归一化会丢失微小缺陷、改变比例。每张正常图仅内存合成一个伪异常；真实缺陷移植只有有效位置掩码才参与，否则沿用现有回退规则；不入库、不落图片、不训练。

正常参考计算均值/尺度并排除近零方差维，三类共用标准化及PCA/SVD投影。显示有效维数、投影秩、各轴解释方差、候选/实际/跳过数量与警告；低秩空轴填0，不随机补点。点选显示图片、类别、来源ID、高维欧氏最近正常距离和近邻ID，正常排除自身及同内容参考，伪异常允许匹配来源正常。配置快照与跳过详情可在结果说明提示中查看。三维远近不一定等于高维距离，更不是异常概率、判别分数或生产阈值；没有绘制任意正常范围球，也未提供自动消融收益结论。后台逐张进度、协作取消、关闭停止轮询，分析任务单实例限流。冻结骨干下，仅训练判别头也不会使同一输入的原始骨干坐标移动，效果仍应看独立真实测试表现。

### 9.10 预处理与跨域，以及本轮预览改进

预处理**与跨域有关系，但不等同于跨域适配**。跨域是训练与实际数据在相机、光照、材质、背景等方面存在分布差异。灰度、CLAHE、去噪有时能减小某些差异，也可能放大差异或抹掉缺陷；它们不是自动域对齐、目标域训练或跨域效果保证。应分别在来源域、目标域真实样本上验证，训练和检测都使用相同处理规则。

本轮已新增“预览预处理”：使用页面当前未保存的设置，对左侧第一张所选正常图显示原图与处理后对照；不保存配置、不登记数据集、不运行模型。为控制界面预览耗时，最长边先缩到 1024 后处理，因此细小缺陷还应在原尺寸评估中验证。伪异常预览也会使用当前未保存的羽化选项；合成方式仍由右侧下拉框选择。预览用于外观检查，不能替代精度评估。

## 10. 模型管理：用途、数学原理、版本评分与持续学习

### 10.1 问题一：这里做什么，是每个品类一个模型吗？如何操作、如何评分？

模型管理维护的是**品类检测方案的版本生命周期**，不是按数据源复制一套完整大网络。后端按 `category` 隔离，不按 `(datasource_id, category)` 隔离：每个品类可以有多个快照，但只有一个当前指针。左树“数据源 → 品类”用于导航和指定准备样本；两个数据源下同名品类共享版本、当前指针及激活/回滚影响。需要独立建模时，应先明确不同品类标识，不要把导航分组当成隔离边界。

当前页面实际操作如下（没有在本页实现的验收/批准不能称为本页按钮）：

| 操作 | 实际行为与边界 |
| --- | --- |
| 准备/重新准备模型 | 弹窗检查数据条件，选择运行模式，从所选数据源预训练组取样；生成版本，结果明确是否已激活。不是一概“准备后待激活” |
| 固化学习快照（原“学习反馈并更新模型”） | `_on_self_learning` 调用 `self_learning_update` → `/self_learning/update` → `service.consolidate`，固化已有学习状态；不保证把界面所有待反馈再训练一遍，也不是隔离候选发布流程 |
| 学习效果 | 跳到学习效果页并带当前品类 |
| 版本历史中的激活 | 选择版本后调用激活接口，展示门控结果；是否允许强制由后端决定，不等于完成独立验收批准 |
| 回滚 | 调用品类回滚接口，保留历史版本；所有同名品类来源共同受影响 |
| A/B 对比 | 与当前激活版本提交比较任务，结果到评估看板查看；不是本页已经展示完整对比报告 |
| 导出/导入快照 | 导出当前激活版本 zip；导入目标品类后不自动激活，应验收后再激活 |

**没有百分制总分，也不应把一次 AUROC 当作综合模型质量。**

- 原“历史最佳验证 AUC”取自 `_category_readiness`：品类全部 `run_type=accuracy` 的 EvalRun 中 `metrics.auroc` 的最大值。并不保证是验证划分，也不是当前版本、当前数据源的评分。本次保留名称但明确标为品类历史参考并提示该口径。
- 新增“当前版本最近精度评估”：复用 `/api/eval/runs` 全部分页，按品类及明确的 `metrics.model_version`（兼容显式 model_id）匹配当前模型；双方都有绑定时不能互相冲突。按 EvalRun ID 取最近完成的有指标记录，排除 running/failed 和其他评估类型；不从 dataset_desc 猜版本，不拿品类最新记录冒充。旧记录无绑定时显示“未评估”，读取失败显示暂不可用。
- 真实 `run_accuracy_eval` 在评估开始固定快照，并写入 `metrics.model_version`、快照元数据 SHA256（存在才记录）、状态；完成后写入 AUROC、AP、F1、阈值、混淆矩阵及误报漏检率。页面显示记录 ID、版本、时间、样本量、数据集描述及元数据哈希提示，可以回查评估记录。Model.metrics 不含这些指标时不补造。
- AUROC/AP 衡量排序能力；单一类别时后端返回 None，显示“—”。F1、误报数 FP、漏检数 FN、FPR/ FNR 来自**本评估集扫描的最优 F1 阈值**，不是生产阈值在线效果。比率按 0～1 原值显示，不换算为“模型得分”。小样本、不同划分和不同采集条件结果不应直接比较。
- “当前版本槽位”只读 Model.metrics.slot_names，展示中文名；缺失显示未知，不把默认配置列为实际已启用分支。

### 10.2 问题二：模型数学上是什么？槽位、版本与持续学习是什么关系？

可将品类模型简写为 `M_c = {记忆库、检测头、分支校准、融合权重、阈值、学习状态}`，共同依赖冻结特征骨干 `z = φ(x)`。骨干可能由不同品类共享，品类快照不是只有一份神经权重：还含槽位状态、校准、阈值、融合与学习状态。外部 backbone 文件仍是运行依赖，不能承诺一个 zip 在任意机器脱离这些资产独立运行。

槽位是**并行证据分支，非串联模型层**。以下是可用机制，不是宣称每个版本都启用：实际启用由数据条件/场景、profile 与配置决定。

| 槽位 | 简洁数学/机制 | 含义与限制 |
| --- | --- | --- |
| sem 正常语义记忆 | 对 patch 特征 `z`，`s(z)=min_{b∈B_normal}(1−cos(z,b))`，再聚合 | 离已知正常外观越远，异常证据越强；不是缺陷概率 |
| disc 伪异常判别头 | `p=σ(hθ(z))`，正常标签 0、伪异常 1，以 BCE 训练 θ | 骨干冻结，学习小判别头；合成异常不保证覆盖真实缺陷 |
| shead 偏离检测头 | 以正常参考的标准化偏离和 margin 目标约束输出 | 输出偏离值而非 sigmoid 概率，不能解释为置信百分比 |
| trad 传统特征距离 | 正常参考标准化手工特征，再计算距离 | 反映纹理/形状等差异，不是深度网络分类概率 |
| blob 斑点 | 多尺度 DoG（高斯差分）响应 | 检测局部亮暗斑点 |
| layout 布局 | 连通区域数量、面积与布局统计差异 | 反映结构/布局变化 |
| inp 图内原型 | 与图内原型/重复结构比较 | 适合图内自相似，非跨品类分类器 |
| tpl 模板差分 | 与标准模板对齐后计算差分 | 依赖模板与对齐条件 |
| color 颜色分布 | 正常参考颜色分布差异 | 依赖颜色信息及光照条件 |
| open 开放集哨兵 | PCA 子空间的偏离检测 | 独立告警，不作为普通融合槽位加入加权和 |

各槽位原始分数量纲不同，先做分支校准 `q_k=C_k(s_k)`；这类校准**不使分数自动成为缺陷概率**。活动分支融合为：

`w'_k = (w_k × confidence_k) / Σ_j(w_j × confidence_j)`，`S = Σ_k w'_k q_k`。

零置信分支不贡献，分母只计算活动证据。融合后根据 normal/gray/anomaly 阈值形成正常、灰区、异常判断，并继续经过定位/后处理等规则，不能仅用一个数学加权和概括全部生产决策。代码中存在 router 相关能力，但当前不实际用于融合，不应画成已经接管线上决策。

**持续学习不是每次反馈重训全部模型。** 冻结骨干不动；正常/缺陷记忆库、检测头、校准、融合权重、阈值等组件只在满足数据条件与门控时有条件更新。反馈进入孵化、筛选、证据约束及候选学习等流程，不应承诺所有反馈立即更新所有组件。

默认候选反馈隔离于生产，需要独立验收、批准、激活才上线。`legacy` 即学是兼容路径，可更新在线内存状态；`consolidate` 是把已有状态固化为快照并登记版本，不等价于候选训练和发布。本页实际仍调用 consolidate；请求不传 auto_activate，后端读取 `self_learning.auto_activate`（默认 false），所以文案不能绝对保证“完成就上线”，也不能绝对保证所有配置下“永不自动上线”。本次只澄清操作与状态，不改发布流程。

## 11. 评估看板：模型阶段、指标与评估入口

### 11.1 只评估初次准备的模型吗？有什么意义？

不是。评估记录描述的是**某个品类模型在某组样本上的一次测量**，不是只属于初次准备阶段，也不是自动刷新的线上准确率。

- 精度评估、噪声鲁棒性：当前页面不指定历史版本，在后台任务实际开始执行时解析当前版本，并构建独立快照副本。运行中的评估不跟随后续版本切换；记录保存实际 `model_version`。因此持续学习后，应先将目标学习状态固化为可评估版本，并按现有发布流程使其成为当前版本，再提交本页面评估；内存中未固化的变化不能当作已评估版本。
- 延迟基准：调用当前在线检测服务，预热后计时，并不固定快照；不能把它当成严格隔离的某版本精度验收。页面将其标注为在线服务，而不是猜测版本。
- 同名品类跨数据源共享模型；评估取样同样按品类与数据划分查询，不是严格按当前工单或单个数据源隔离。比较时必须核对记录中的品类、版本、样本量和数据描述。

评估的意义是检查模型区分正常/缺陷的能力、实际工作点的检出与误报，以及计算成本和抗扰动能力。初次准备后可检查基线；学习后的固化版本可重复测量，但应尽量保持样本和测量条件一致。小样本结果仅是检查参考，不能直接承诺上线质量；训练划分的结果也不能冒充独立测试效果。

### 11.2 记录补齐了哪些指标？

记录表新增**版本、样本数、检出率、误报率**，保留 AUROC、AP、F1 和延迟；选中精度记录后展示完整混淆矩阵、准确率、精确率、检出率与特异度等详情。

- 检出率 = `TP / (TP + FN)`，即真实缺陷中被判出缺陷的比例，越高越好。
- 误报率 = `FP / (FP + TN)`，即真实正常中被判为缺陷的比例，越低越好。
- 计数缺失、分母为零时显示未知或无定义，不填成 0%；本页不再把漏检率作为主展示指标，也不是仅改标题而保留原漏检率数据。
- 本页精度评估的 F1、混淆矩阵及派生率来自**在本次评估集上扫描得到的最佳 F1 阈值**，不是生产阈值效果，也不会自动修改生产阈值。AUROC/AP 是排序指标，不是百分制总分。记录里的逐图原始 `pred` 使用生产决策，不能用它重算并冒充这里的最优阈值矩阵。
- 缺少 `latency_pass` 的旧记录不再被冒认为精度与延迟完整通过。页面参考标记不是独立发布批准，也不能替代检出率/误报率业务预算验收。

列表改为读取全部分页，不再只显示首 50 条。其他页面的全局检出率替换仍需逐页按各自分母核实，本节不宣称已全部完成。

### 11.3 为什么原来只能下拉选择一项？怎样调整？

三类评估是三个独立后台任务，测量目的与成本不同，不需要强制一次全跑。本次取消隐藏在下拉中的类型入口，改为三个直接可见的运行按钮，各有样本上限：精度默认 20 张、延迟默认 20 次测量、鲁棒性默认 12 张。延迟基准另有 3 次预热，样本不足时可能循环图片，不能将测量次数理解为独立图片数量；它不使用精度表单的数据划分。

本页提交期间及任务执行期间禁止重复提交，以免并发争用资源影响计时；只跟踪本页提交的任务 ID，并用任务轮询补充消息通知。进度达到 100% 不等于任务完成，仍以任务终态为准。鲁棒性默认约为样本数 × 16 次前向，提交前明确确认成本，不自动跑全量数据。

### 11.4 鲁棒性改为页面内嵌

选中噪声鲁棒性记录后，在页面详情区直接显示基线 AUROC、各扰动面积及衰减曲线，不再要求双击打开独立弹窗。

- 新记录保存真实 `levels`；横轴按位置显示真实强度标签。历史记录缺少完整强度信息时只能显示档位序号，不补造强度。
- `A_rob` 是未归一化的 AUROC-扰动强度梯形面积。默认区间为 0～0.8，理想面积为 0.8，不是 1；不同强度区间的面积不能直接比较。
- 基线是原图；当前模糊公式在强度 0 时仍有 sigma=0.5 的模糊，不等同于无扰动。
- 后端进度现在覆盖基线和全部扰动前向；正常/异常两类不齐时明确拒绝计算 AUROC。

同时修复精度样本上限为 1 时，零配额一类可能意外读取全部图片的问题。

### 11.5 验证状态

新增 `tests/smoke/test_eval_dashboard.py` 的 7 项定向测试，覆盖三类入口、提交互斥、任务隔离与终态、指标缺失、内嵌曲线、零配额取样和鲁棒性进度/档位持久化；测试使用离屏 Qt 与模拟数据，不进行真实模型前向。编辑器对页面、服务与测试文件诊断均为空。当前终端执行受环境错误 `Toolhost terminal commands must be routed through the agent runtime` 阻断，unittest 与 compileall 未实际运行，不能声称测试通过；也未进行真实桌面人工验收或全量评估。

## 12. 实时监控：产线、队列与并行人工反馈

### 12.1 工单与产线分别是什么？暂停、停止和恢复有什么区别？

工单组织一次检测任务的数据源、复核与运行配置；本系统的“产线”是按工单消费图片并保存检测的后台执行管线，不是物理车间产线编号。工单的 active/closed、是否存档、管线的 running/paused/auto_paused/stopped 是不同字段，不能互相等同。新建工单默认暂停，准备模型后仍需主动恢复产线。

- 暂停：暂时不继续领取新任务，保留回队编排，适合现场检查、等待人工复核或调整安排。
- 停止：设置 stopped 并清空回队配置，适合结束当前排产。它不删除原图、普通未检数据、检测与反馈，也不是关闭或删除工单。
- 恢复：设置 running，从暂停或停止重新允许后台领取任务；没有名为 start 的工单控制接口，页面“恢复”承担开线动作。模型未准备好时消费者会跳过该品类。
- 暂停/停止均不强杀已经开始的推理，操作后仍可能有一条在途结果落库。
- 开启人工复核后，待反馈积压默认达到 30 条会背压自动暂停，下降至 10 条及以下可自动恢复。手工暂停和 stopped 不会由这条背压逻辑恢复；但“固化后自动恢复”是另一条路径，可将 stopped 设回 running，因此不能承诺停止后绝不自动恢复。

实际主流程是：数据源导入并挂接工单 → 准备对应品类模型 → 恢复产线 → 领取图片并检测落库 → 实时监控与人工复核 → 按需回队重检、固化或候选治理 → 导出报告。数据管理、模型管理、标注反馈、学习效果和评估看板各承担不同环节。

**实现边界：**当前关闭工单的接口仅改 status，消费者主要按 pipeline_status 判断，不应将“关闭”当作已可靠停线；存档与运行状态也存在分支边界。本轮未擅自重构后端生命周期，结束任务应明确执行停止并检查状态。

### 12.2 “学习提升”实际做了什么？

当前按钮调用工单 learn 接口，但实现是对挂接数据源的品类逐一调用 consolidate，固化已有内存学习状态、尝试登记版本，并非遍历本工单待反馈样本训练，也不保证效果提升或激活。因此已改名为**固化学习快照**，执行前确认范围与自动恢复风险。

生产反馈接口保存 `candidate_queued / consumed=False` 的候选待消费反馈，不直接修改生产模型；固化接口取已有 consumed=True 的反馈血缘，不会自动消费这些新候选。工程师可调用 `POST /feedback/{feedback_id}/candidate`，传入当前真实 `parent_version`，显式构建已落库反馈的独立候选，随后跟踪返回的 task_id。已构建反馈重复调用返回原候选，不重新训练；引擎存在失败或 prepared 意图时仍须按原事件恢复，不能换父版本绕过。

候选任务成功后，取实际返回的 category/version_num，依次调用 `/candidates/{category}/{version}/acceptance`（独立 old/new test 图片 ID）、`/decision`（管理员、真实 report_hash）、`/activate`。验收失败不得批准，批准不等于上线；激活结果的 model_mirror 与引擎 current 指针一致才表示模型绑定完成，prepared 发布可走 `/candidates/{category}/recover`。不把本页按钮描述成自动学习闭环，也不承诺效果提升。

特征 revision 是另一条门禁：draft → evaluated → approved → active 需要真实独立评价、难例准入与数值等价证据，active 仅表示可绑定；生产绑定还须调用 `/models/feature-revisions/production/bind` 并核对真实模型快照。自动发现且 extractor=not_implemented 的新特征不能因排队或模型学习成功而自动上线。自动恢复目前即便没有成功固化品类也可能执行，恢复产线不代表模型已更新成功。

### 12.3 队列各列及回队的意义

队列是工单挂接数据源按品类动态计算的检测分组视图。每批数量由数据源 batch_size 配置，默认 30，不是永远固定 30。模板和预训练分组有独立规则。

本次将队列从窄左栏移到底部全宽区域，支持拖动上下分隔条调整高度；拆分合并计数，并为身份字段提供换行与完整提示。

| 列 | 含义 |
| --- | --- |
| 批次 | 动态检测分组批次名，不等同于导入 Dataset 批次 |
| 数据源、品类 | 图片来源与模型所属品类 |
| 图片 | 该分组图片 ID 数量 |
| 检测记录 | 这些图片的 Detection 记录数，不是去重的已检图片数 |
| 异常记录 | 其中 is_anomaly=True 的检测记录数，不等于人工确认缺陷数 |
| 反馈记录 | 关联反馈记录数，当前批统计未排除作废反馈 |
| 待关注 | 检测异常占比至少 50%，或反馈记录至少 3 条的经验提醒，不是已证明错检 |
| 回队 | 此批是否登记了优先重检请求 |

**统计边界：**现有批统计按图片集合查询，未限制当前工单或 target_type，可能累计其他工单、旁路检测及重检记录。因此不能拿“检测记录/图片”当严格进度，也不能把首个计数不足的批次当后台正在处理的任务。本轮移除了这一误导高亮，并将“错检高发”改为“待关注”。

回队用于模型或条件变化后重新测量一组图片：固化本批图片 ID 与回队代次，在本工单内优先于普通任务处理，最近回队的批次优先；运行中也能回队。成功重检新增 Detection，保留旧结果，全部完成后移除该次回队请求。取消回队不撤销已开始的推理；人工提交反馈也不会自动回队。

**队列与消费者并非完全一致：**展示使用动态分组，普通消费者目前直接遍历挂接数据源中的图片，未复用同一套预训练排除规则；空转积压统计也有不同过滤条件。本轮不把展示队列包装成严格执行日志，统一后端选择规则应另作针对性修复。

### 12.4 人工反馈如何与实时检测并行？

原页面取消跟随后仍可能因选中下标为 -1 被最新帧覆盖。本次修正该分支，并提供明确的**锁定当前画面、返回最新、进入标注反馈**入口。

- 锁图只暂停主图自动切换，后台检测、实时轮询、条带与曲线继续更新，不是暂停产线。
- 打开反馈时深拷贝当前检测信息，固定 detection_id；反馈窗口改为非模态，允许主页面继续操作，重新跟随最新帧不会改变已打开窗口的目标。
- 同时最多打开一个反馈窗口，避免重复误标；图片回调校验检测目标及关闭代次，拒绝关闭后迟到的图片。
- 条带只保留近 50 帧，不是完整持久复核队列。待复核记录应进入标注反馈页处理，不要求人在每帧经过时立即操作。
- 实时流是增量轮询已落库 Detection，并不是浏览器显示一帧才触发一次检测；人工窗口不增加检测前向次数。本次布局与锁图不改变原推理成本。

### 12.5 人工标记后图片和记录流向哪里？

页面增加可展开的全局数据流说明，区分生产路径、复核路径和候选发布路径：

```text
数据源 / 导入批次 → Image 原始图片
                         ↓ 工单后台领取（模型已准备）
                     Detection 检测记录
                       ├→ 实时监控：滚动显示 / 锁图回看
                       ├→ 标注反馈：按规则查询持久待复核记录
                       └→ 工单统计 / CSV 导出
                                  ↓ 人工提交
                          Feedback 反馈记录
                                  ↓ 候选待消费（生产模型不变）
                    独立候选构建 → 验收 → 批准 / 激活

回队请求 → 原图片再次检测 → 新 Detection（旧记录保留）
固化学习快照 → 保存已有内存态（不是自动消费全部待反馈）
```

反馈记录保留人工标签、类型、区域、操作者及检测关联；已有 Image 不因标记迁移原批次。未登记图片才进入按品类的反馈回流系统 Dataset，标记 split=feedback、source=feedback。提交时可能额外调用当前模型预测以记录 pre，但候选隔离分支不更新在线模型、不自动构建候选、不自动回队。

开启工单人工复核时，工单全部产线检测可纳入待复核；关闭后，非灰区不再由该开关入队，但灰区仍有独立入队规则。有效且非 open_alert 的反馈可使记录退出待复核。开关关闭不删除历史反馈，也不会自动解除此前的 auto_paused 状态。

### 12.6 导出 CSV 是什么？为什么导出？

用于留存本工单检测明细、交接与外部核对，不是训练输入或模型效果证明。文件包含汇总段和明细段，按 Detection.workorder_id 取本工单记录，包含重检及当前接口范围内的其他检测类型，不只最新一轮，也不只人工确认过的样本。

- 汇总：工单信息、时间范围、总数、正常/异常/灰区数、不良率、平均与 P95 端到端延迟及缺失数、有效反馈与误报/漏检反馈计数。不良率按（异常+灰区）/总数计算。
- 明细：detection_id、created_at、image_path、category、decision、final_score、latency_ms、n_feedback、corrected。
- 明细 latency_ms 来自 Detection.latency_ms，与汇总的端到端口径不同；corrected 只表示存在有效误报/漏检反馈，不表示已覆盖原判定或训练成功。
- 不包含完整人工标签、框选、反馈详情、模型版本和候选状态，不能当完整审计备份；文件为带 BOM 的 UTF-8 CSV。

## 13. 标注反馈与特征工程：人工复核开关、候选反馈和生产特征隔离

### 13.1 新建工单不勾选“人工复核”后，标注反馈页是否仍然工作？

仍然工作，但这个开关不是“关闭所有复核”的总开关。灰区检测有独立的待复核入队规则；关闭人工复核后，灰区仍可能出现在待复核队列。开关打开时，工单的非灰区产线检测还可以额外进入人工复核流程；关闭后，非灰区不会再因为该开关进入队列。试检旁路不进入这条产线待复核队列。

人工提交后会创建或更新 `Feedback` 记录，并把生产反馈放入候选隔离路径，通常表现为 `candidate_queued`、`consumed=False`。这表示反馈已落库、等待候选流程消费，不表示生产模型已经更新、候选模型已经构建或版本已经激活。历史反馈不会因为关闭开关而删除。

作废反馈只会让该反馈不再计入相关统计和曲线；是否再次进入待复核还取决于检测当前阶段及其他入队条件，不能把“作废”解释成必然回队。若反馈已经进入候选或某个模型版本，需要重新验收或回滚版本消除影响。

### 13.2 特征工程页的“生产事实只读，候选配置隔离”是什么意思？

它表示页面左侧展示的是当前检测使用的生产特征事实，不能在表格内直接编辑；右侧操作先生成分析证据或登记候选 revision，不会直接替换生产提取器。真正影响生产需要经过评估、准入、批准，并显式绑定生产指针。候选 revision 的状态 `active` 只表示它满足门禁、允许绑定，不等于已经切换到生产。

当前页面的候选能力不是完整的特征实验器：没有在页面内编辑每个特征组参数、scoring 或消融组合。登记候选 revision 只是按当前启用组、当前 scoring 和备注保存一份 draft manifest。因此“登记候选”不应理解为已经完成了一次新的特征训练。

### 13.3 为什么默认特征会被设置页“一键清理”清空？

默认传统特征来自代码注册表和随项目打包的提取器，当前约 15 组、约 200 维；DINO patch token 的 384 维属于另一类主干信息。设置页“一键清理”不会删除这些默认特征定义，也不是清缓存按钮。它主要修复或删除没有工单/数据源有效归属的检测、反馈、批次、图片登记和卡死认领，并可能删除 storage 中应用生成的孤儿文件；对无归属数据执行前应确认，因为操作不可恢复。

因此如果页面看起来“特征为空”，应先区分品类是否已准备 trad 槽位、生产表示是否可用、接口是否返回当前特征组，而不是认为一键清理删除了默认特征。当前页面对未返回的组参数显示为权重/尺度缺失，而不是把空字典伪装成完整参数。

### 13.4 “当前档案、候选分析与治理、重建、revision”分别是什么？

| 页面动作/对象 | 实际含义 | 不代表什么 |
| --- | --- | --- |
| 分析当前特征影响 | 用少量 test 样本生成传统特征贡献评估证据，保存为 contribution 类型评估记录 | 不是新的生产配置，也不是自动提升准确率 |
| 登记候选 revision | 按当前生产启用组和 scoring 登记 draft manifest | 不是已经训练、验收或激活 |
| 重建候选表示 | 提交 `model_prepare` 后台任务，重提特征、重建库并生成未激活版本 | 当前接口不接收 revision_id，因此不是“选择某 revision 后重建” |
| revision | 一份带特征组、实现哈希、预处理、数据划分和基线签名的候选配置版本 | `active` 不等于生产指针已切换 |
| 生产指针 | 独立记录当前实际绑定的 revision | 不能只看 revision 列表中的单个状态字段判断生产是否使用 |

合理流程是：

```text
生产特征事实（只读）
  → 分析当前特征影响（小样本证据）
  → 登记候选 revision（draft）
  → 独立重建未激活版本
  → 评估 / 准入 / 批准
  → 显式绑定生产指针
```

### 13.5 能否直观看到特征对检测结果的影响？

当前页面已把“生成当前档案”改名为“分析当前特征影响”，并明确它使用少量 test 样本生成传统特征贡献档案；结果区也标明这是评估证据，不是生产配置。当前实现展示档案状态、测试样本数和生产特征组/维度，但还没有在特征工程页内嵌“当前工单每张图的特征贡献瀑布图”或逐图多数据集对比图。

如果要增加可视化，建议限定为当前品类/当前工单的小样本分析：显示各特征组的贡献排序、正常与异常样本分布、代表图片与检测结果，并同时显示样本数、模型版本、特征签名和“非生产决策”的提示。不能用三维投影距离直接当异常概率，也不能在没有真实对照样本时宣称某特征提升了检测效果。当前先完成了准确文案和状态边界，没有新增未经后端支持的伪可视化。

## 14. 学习效果、存档统计与系统设置

### 14.1 “线上学习证据”到底证明什么？

“线上”指真实产线反馈路径产生的记录，不是“提交反馈后生产模型立即变化”。反馈状态还需区分已落库、候选排队、候选构建、验收和激活；`candidate_queued` 只证明反馈进入候选队列，不证明已经学习或已激活。页面四张图分别是：翻案曲线（反馈样本当前是否由错判转为正确）、误判率趋势（复核样本的 FP/FN 比率变化）、权重演化（学习快照中的融合权重变化）和滚动判对率（真实反馈流中的滚动正确率）。这些是过程证据，不能单独证明生产精度提升；应结合评估看板的独立评估和当前生产版本判断。

### 14.2 离线回放的学习曲线是什么？

离线回放使用标注数据的独立副本模拟多轮反馈，横轴通常是累计反馈数，纵轴可以是 AUROC、F1、已反馈重测准确率等。它用于回答“如果按这种反馈顺序学习，模型表现如何变化”，不是当前产线实时指标，也不会直接激活生产模型。当前页面新增末轮锚定集的真实检出率和误报率：检出率 = `TP/(TP+FN)`，误报率 = `FP/(FP+TN)`；分母为零或后端没有该混淆矩阵时显示未知，前面轮次不伪造数值。

### 14.3 槽位消融等分析是不是持续学习自动产生？

不是。槽位消融、单槽位×缺陷类型、槽位相关矩阵和传统特征组贡献，都是主动生成的评价/实验档案，不是每次持续学习自动产生，也不直接修改生产。槽位不是特征的同义词：槽位是专家检测能力的评分、状态与更新单元；传统特征组（如 GLCM、边缘、颜色等）只是 `trad` 槽位的输入分组。当前页面把这些内容放在学习效果的主动实验/健康审计区域，便于把“学习证据”和“实验分析”区分开。

### 14.4 存档统计页面做什么？

它以工单为边界管理历史数据：进行中/已存档工单切换、存档、还原、删除，并聚合该工单的检测和复核结果。主要指标包括检测数、复核覆盖率、真实不良率、误报率、检出率、推理耗时和端到端耗时；无标签或分母为零时显示未知，不用不良率冒充模型检出率。

“产线健康信号”不是另一个准确率，而是帮助定位产线风险的运营信号：灰区率高说明复判压力可能增加；未解释信号/open 表示现有特征体系无法解释的异常预警；对位预警提示治具、相机或传送带可能发生偏移。“缺陷类型帕累托”按人工复核确认的真实 `defect_type` 计数并排序，帮助优先处理占比最高的缺陷类型；未标注类型单列为“未标注”。

### 14.5 为什么全局用“检出率”而不是“漏检率”？

对外展示统一使用检出率：真实缺陷被系统检出的比例，公式为 `TP/(TP+FN)`。`FN` 仍然保留为内部漏检样本数，便于追溯。误报率为 `FP/(FP+TN)`。两者都必须基于有真实标签的混淆矩阵；缺标签或分母为零显示“—/未知”。因此工单不良率、灰区率、反馈覆盖率都不能替代检出率。旧接口字段 `fn_rate/fnr` 可以继续兼容，但页面不应再把它直接称为漏检率。

### 14.6 系统设置如何影响其他页面？

系统设置分成几类：

| 设置组 | 主要生效位置 | 对检测效果/运行的影响 |
| --- | --- | --- |
| 推理管线 | 顶栏预算、评估/验收参考、人工复判积压检查 | 影响背压和达标参考，不改变缺陷分数 |
| 数据目录 | 数据管理导入框默认路径 | 只改变默认路径，不搬迁数据 |
| 在线学习 | 学习巩固和资源让行检查 | 自动激活可能切换生产模型，并行开关影响资源竞争 |
| 评估 | 延迟基准参数（部分配置尚未接入） | 未接入项保存后不改变当前评估请求 |
| 告警通知 | Webhook、批量告警监视器 | 影响外部通知，不改变单帧判定；部分参数需重启后端 |
| 自动归档 | 后续检测图像复制与登记 | 增加写盘，不自动入训，不修正检测结果 |
| PLC 触发 | PLC 触发接口取图目录 | 影响外部触发取图，不启动目录监听 |
| 日志 | 后端运行日志 | 需重启后端，不改变检测结果 |
| 业务预算与保留期 | 统计/候选验收、保留期预览审批 | 是业务线，不是算法阈值；保存不自动删除数据 |
| 校准隔离、Blob GPU、额外正常批次 | 模型准备/引擎加载 | 可能需要重新准备模型或重新加载引擎，已有快照不自动改变 |
| 自检、清理、审计 | 设置页与数据维护 | 清理可能删除孤儿业务数据/应用生成文件，不清理默认特征、不重训模型 |

保存配置不等于全部即时生效：告警监视器和日志等需重启后端，校准/训练数据变更需重新准备模型，Blob GPU 需重新加载品类引擎。`trigger_min_feedback` 当前未找到运行时消费路径，不能把它宣传为可靠的自动巩固触发器。

### 15.2 五项重点的当前完成状态

1. **工单生命周期与停线语义：已实现最小闭环。** 关闭、存档或停止会停止管线、释放在途认领并拒绝旧 worker 迟到写入；关闭/存档不能恢复。工单状态摘要已综合队列和管线状态。
2. **队列展示与消费者统一：已实现。** 二者复用检测分组、当前工单、预训练/模板排除、回队代次和失败口径；队列 API 现在区分可检测、在途和失败数量。
3. **特征工程样本贡献分析：已实现样本级特征组分析。** 页面展示 test 评价档案中的特征组 AUROC 与留一掉分，并增加逐图 `image_id / baseline / ablated / contribution` 查询；明确这不是生产模型逐图因果贡献。
4. **自动增强同集消融：已实现最小真实闭环。** 后台固定样本和配置，分别拟合基线与关闭单因素增强的模型，真实计算指标并持久化；默认小样本单种子，仅用于趋势比较，不自动激活。
5. **均值/P95展示：已实现。** 工作台和存档统计页展示检测处理耗时均值及 P95；口径为检测处理开始至保存前，不含采集、网络、落库和告警。
6. **候选配置到生产绑定：已补齐入口闭环。** 反馈可进入幂等候选构建，再经独立验收、批准/激活和 Model 镜像绑定；特征 revision 仍需独立评价与生产指针绑定，不能由候选反馈自动伪造上线。
7. **反馈阈值和延迟基准默认值：已接入。** 达到 `trigger_min_feedback` 只生成待巩固状态和审计记录，不自动训练或激活；`benchmark_n_images`、`benchmark_warmup` 统一作为 UI/API/后端默认来源，显式请求参数仍优先。
