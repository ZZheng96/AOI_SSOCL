# AOI_sys 重构设计：模型管理页（数据源→品类→模型状态）

> 日期：2026-08-29 · 状态：已实施（冒烟 25/25 通过）
> 触发：用户评审指出原模型管理页三类问题——① 用户视角困惑信息（内部代号/槽位/CDF 校准等术语）；② 顶部架构示意图不正确且无用（把三槽位并行画成串联）；③ 模型管理不匹配当前工单、同品类罗列大量版本、结构与数据管理页数据源结构不一致。

## 1. 问题清单（原页面）

### 1.1 用户提出的三点（代码佐证）
| 问题 | 佐证 |
|---|---|
| 困惑信息 | 页面直接出现 "引擎"、"sem/disc/shead 槽位"、"问题三"、"CDF 校准" 等算法内部术语；模型来源 origin 直接显示 `engine_fit`/`self_learned_engine` |
| 示意图错误无用 | CascadeDiagram 把三槽位并行打分加权融合错画成串联流水线；图无任何交互，占首屏黄金位置 |
| 不匹配工单/结构不一致 | Model 表只有 category+version，无 workorder_id/datasource_id 字段（backend/db/models.py L224-237）；页面按品类平铺所有版本，与数据管理页「数据源→品类」树完全不同构 |

### 1.2 补充发现
1. **准备模型前后端能力断层（最严重）**：后端 `ModelPrepareRequest` 早已支持 `datasource_id`（schemas.py L236-242，routes_models.py L247-286 从数据源预训练组取样本），但原前端 PrepareModelDialog 从不传该参数 → 用户配置了数据源分组，准备模型却仍从图库全量取数。
2. **"扫描模型"按钮混入用户界面**：磁盘扫描是运维操作，不属于用户日常流程。
3. **"分数校准"卡是旧功能墓志铭**：功能已下线，只剩说明文字。
4. **动作堆砌无流程主线**：准备/激活/回滚/A/B/学习平铺，用户不知道"下一步该做什么"（readiness 状态机后端已有，前端未用）。
5. **版本历史平铺**：16 个版本全量铺开，当前版本淹没其中；回滚不显示目标版本，属盲操作。
6. **指标噪音**：表格罗列大量引擎内部指标，用户只关心"验证准不准"。

## 2. 方案与决策

**结构镜像数据管理页**：左侧「数据源→品类」导航树（当前工单口径：有工单取 `wo["datasources"]`，无工单回退全量数据源列表；每源异步 `datasource_groups(id)` 填品类节点），右侧品类模型面板。后端零改动。

```
模型管理页
├── 左：数据源→品类树（品类节点文本 = 品类名（v16 · ⑤ 已投产），readiness 驱动）
└── 右：品类面板
    ├── 状态头：品类名 + 阶段徽标（readiness stage_cn 配色）+ 下一步提示（next_action）
    ├── 当前状态卡：当前版本 / 历史最佳验证 AUC / 待学习反馈 / 数据来源
    ├── 操作卡：准备模型（主）+ 学习反馈并更新模型（主）+ 学习曲线（跳转）
    └── 版本历史卡（默认折叠）：选择/版本/来源/验证指标/操作；回滚显示目标版本
```

**关键决策**：
1. 页面主线 = readiness 状态机（empty→insufficient→ready→trained→validated→active），阶段徽标 + next_action 引导用户，取代动作堆砌。
2. PrepareModelDialog：品类/数据源由树选中带入（只读），数据条件自动判定（工单条件优先，无工单用数据体检建议），**提交必传 datasource_id**（补断层）。
3. 术语清理三管齐下：UI 文案改写 + `ORIGIN_NAMES` 映射（DB origin→中文来源）+ `_WARN_JARGON` 翻译层（后端体检警告逐条替换内部术语）。
4. 版本历史折叠收纳；旧 demo4 数据（version>=100 且 metrics.engine 为 demo4/空）前端过滤不显示（DB 未清理，`_is_demo_legacy`）。
5. 激活质量门控对话框文案用户化："锚定集 AUROC" → "验证图上的准确率"。

## 4. 重要发现与坑（后续改进参考）

1. **TaskMonitor 没有 register 方法**：`ui/widgets/task_progress.py` 的 TaskMonitor 只有 `task_updated = Signal(dict)` 全局信号。页面跟踪任务的标准模式是：`__init__` 里 `monitor.task_updated.connect(self._on_task)`，提交后记录 `self._task_id`，`_on_task` 内按 `str(t.get("id"))` 过滤匹配（参考 eval_page.py L122-123、L337-345）。**不要凭直觉编造 register/on_done 回调式 API。**
2. **precheck 接口 resolutions 是 list 不是 dict**：`/api/models/precheck/{cat}` 返回 `resolutions: [{width, height, count}]`（按图数降序前 3，routes_models.py L398-400），无 `native/display` 键。前后端契约不一致静态检查查不出，offscreen 冒烟才暴露（AttributeError: 'list' object has no attribute 'get'）。
3. **后端警告文案含内部术语，会原样漏到 UI**：precheck warnings 里有 "CDF 校准"、"disc/shead 判别头"、"tpl 模板差分槽位"、"L0/L1a/L1b"（routes_models.py L405-434）。前端加 `_WARN_JARGON` 替换层兜底；**根治应在后端**，但后端警告也被其他端消费，暂前端翻译。
4. **readiness 的 active_version 已带 "v" 前缀**（"v16"），拼接时不可再补 "v"（否则 "vv16"）。
5. **ui/widgets/__init__.py 是空文件**：`from ..widgets import TaskProgressBar` 会 ImportError，必须 `from ..widgets.task_progress import TaskMonitor, TaskProgressBar`。
6. **前端能力断层类 bug 的排查方法**：对照 schemas.py 请求模型与 api_client.py 发送 payload，凡后端有字段前端不传的都要警惕（本次 datasource_id 即此类型）。
7. **树异步填充竞态防护**：`datasource_groups` 回调到达时树可能已重建，需 `node.treeWidget() is not None` 防护（复用 data_page.py 模式）。
8. **Model 表与数据源/工单无 DB 层关联**：本次"匹配工单"仅前端树口径（工单→datasources→groups→categories）。若后续要多工单隔离同名品类模型，需 Model 表加 workorder_id/datasource_id 字段（本次未做，属结构性欠债）。
9. **冒烟脚本 import 路径**：tests/ 下脚本需 `sys.path.insert(0, 父目录)`（server.py 在工程根）；且 Select-String 过滤 `GET /api/file` 日志可大幅降噪。
10. **precheck 模板存在性契约（2026-09-01 UI 走查修复）**：后端原先只返回 `counts.template` 和提示文案，遗漏前端门禁直接读取的顶层 `has_template`。结果是同一准备模型弹窗同时显示“已有 4 张模板图”和“该品类还没有模板图”。现由 `/api/models/precheck/{category}` 明确返回 `has_template = counts["template"] > 0`；新增或调整体检字段时必须同步核对前端 `_fill_precheck` 的直接读取字段，不能只依赖提示文本。

## 5. 快照导出/导入复用（2026-08-30 新增）

**功能**：模型页新增「导出当前版本」「导入快照」。后端：
`GET /api/models/{category}/snapshot/export?version=v{n}`（缺省=当前激活版本，
FileResponse 打包 zip，内含 export_manifest.json 记录 category/version/导出时间）；
`POST /api/models/snapshot/import`（multipart：zip + 目标品类名，允许跨品类复用）。
导入流程：校验关键文件（cfg.yaml/slot_state.pkl/weights.json/decider.json/
calibrators.npz/meta.json）→ 解压到 v{下一版本号}（不覆盖、防 zip-slip）→
meta.json 记录 imported_from → 修正 cfg.yaml 绝对路径 → 登记 Model 行
（origin=uploaded）→ **不自动激活**（不写 current.json），用户验收后手动激活。

**关键发现（后续改进参考）**：
1. **导入必须先落 Model 行再调 register_engine_snapshots**：扫描器会把"不在任何
   数据源品类中"的快照目录当孤儿归档到 _archive/ 并删 Model 行（2026-08-30 MPDD
   残留治理）。导入品类往往无数据源数据，必须靠 origin="uploaded" 行豁免——
   扫描器的孤儿归档、无血缘切指针（current.json 移除）、孤儿 metrics 标记、
   DB 残留行清理四处处均已对 uploaded 豁免。
2. **跨机器路径只有 cfg.yaml 需要修**：slots.disc/shead 的 init_from 与
   backbone.checkpoint 是源机绝对路径，本机不存在时按 engine.base_cfg 同名项
   替换、无对应则移除（disc/shead init_from 缺失仅影响建壳初值，随后被
   slot_state.pkl 覆盖，见 slots/disc.py:157 os.path.exists 守卫）。meta.json/
   weights.json 无路径字段；ssocl/regress_gate.json 的 anchor_paths 无法映射，
   load_snapshot 对缺失路径有容错（降级打印警告），保持原样。
3. **版本号幂等**：导入固定落 v{max+1}，重写 meta.version；zip 兼容平铺包与
   单顶层目录包裹包。
